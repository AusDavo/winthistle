Channel Opener

Premisewhat this is for

The work is coordination, not cryptography

The manual process works. What makes it arduous is that a human is holding the state machine in their head: which pane is which peer, which prompt wants base64 and which wants raw hex, which pane has --no_publish, how much reserve LND will demand once the new channels exist, and how many of the ten minutes are left. Every one of those is mechanical, and every one of them is a place to lose a channel.

So this tool owns the state machine and the clock, and hands the human back exactly two jobs: build the transaction in the wallet you already use and sign it. Nothing else should require a decision under time pressure.

Job one · attribute the outputs

A funding output is a P2WSH 2-of-2 with a peer. No signing wallet can tell you which peer it funds, at what amount, or that two were not swapped. Sparrow shows you payments to unrecognised addresses. This tool prints the plan that gives them names.

Job two · hold the gate

Get all n channels to chan_pending — the receipt that each is recoverable by force-close — and only then let the transaction reach the network. That is I·1, and it is the whole safety argument.

ScopeOne LND node, one funding transaction, n channels. It builds nothing, holds no keys, selects no coins, derives no addresses, and opens no socket except to your LND. It assumes a wallet with coins in it — hot, cold, single-sig, multisig. Which of those does not matter to this program.
Invariantsload-bearing

Three rules that shape everything else

These come from LND's own protocol constraints, not from preference. Each carries a source citation so you can verify it rather than trust this page. There were four; the second dissolved, and its dissolution is recorded below rather than quietly dropped, because an invariant that disappears without explanation is indistinguishable from one that was abandoned.

I·1

Publish only once every channel is already recoverable.

LND's "DO NOT PUBLISH" warning is about ordering, not authorship. The condition that actually matters is that the transaction must not reach the network before every channel has received its peer's funding_signed — the counterparty signature on our initial commitment transaction, which is precisely what lets a force-close recover the funds.

In funding/manager.go, funderProcessFundingSigned (:2718) emits chan_pending (:2897) strictly after CompleteReservation(nil, commitSig) (:2813) has stored that signature, and after WatchNewChannel (:2886) has handed the outpoint to the ChainArbitrator. The broadcast block sits between them at :2829, guarded by completeChan.ChanType.HasFundingTx(). So n chan_pending events is exactly the safe condition — and we gate on it: no_publish is set on every channel, not all but the last.

The citation used to name handleFundingSigned, and no such function exists. It is not a rename — there is no handleFundingSigned at any version and there never was. The ordering was right and the name was ungreppable, which is how a citation stops being checkable. Corrected here, in CLAUDE.md and in the handoff.

And every line number on this page moved once, for a duller reason. The build was pinned to lnd@v0.19.3-beta from its first commit, with no rationale recorded anywhere — a tag already a year old that day — while the node it exists to arm had gone two minor releases further. It now runs v0.21.2-beta in go.mod and in the regtest harness, and the citations here were re-read against that tree rather than assumed. Nothing in the safety model turned out to be wrong: funderProcessFundingSigned's ordering, NoFundingTxBit's four gates, the skip_finalize tail of PsbtIntent.Verify and the 2016-block horizon all survive unchanged. About thirty line numbers did not, which is the same way handleFundingSigned happened — a citation nobody can find is a citation nobody checks.

I·2

Dissolved — and this is the record of why.

I·2 read: the app holds the last signature. Signers returned partial signatures, combining and finalizing happened in-app, and no external party ever held a broadcastable transaction. It existed for exactly one reason — so that nothing could broadcast before the I·1 gate opened and defeat it from outside.

After the inversion there is no "before the gate opens." Every channel reaches chan_pending at step 6; you do not sign until step 7. A wallet holding a fully signed transaction front-runs nothing, because every channel is already recoverable by force-close. The invariant is not relaxed — it has nothing left to protect against. The m−1 signing dance that assisted mode specified is deleted with it.

The single-sig caveat becomes moot rather than unmet. It used to say that a single-sig wallet returns a complete transaction, so there was no partial-signature path to hold it up in, and that on single-sig this property rested on the operator's setup rather than on structure. That was an honest limit on an invariant that now has nothing to reach. Which kind of wallet you sign with stopped mattering to this program, and it should stop pretending otherwise.

This is not a licence to add a broadcast path. I·1 still says the app publishes once, after n receipts. What dissolved is the claim about who else may hold the bytes.

I·3

The TXID must not move after verification.

LND commits to the funding outpoint at psbt_verify: "no inputs or outputs can change, only signatures can be added. If the TXID changes between this call and the publish step then the channel will never be created and the funds will be in limbo." So the app hashes the verified transaction and refuses any returned PSBT whose unsigned TXID differs, naming the device that did it.

I·3 now carries the weight I·2 used to. It is the only load-bearing check on what comes back from the signing wallet, which makes the next paragraph the most important one on this page.

That check is not a duplicate of LND's, because LND's is narrower than the sentence above sounds. PsbtIntent.FinalizeRawTX compares the outputs and the inputs' previous outpoints and stops — "the fields in the PSBT part are allowed to change" — and sequence numbers, version and locktime live in the wire transaction rather than in the PSBT part. CompileFundingTx then takes the channel point from the transaction it was just handed. So a returned transaction with different sequence numbers has a different TXID and LND would adopt it. Nor does LND check the signatures: verifyInputsSigned only asserts that each input has something attached. Both gaps are closed before LND is asked.

This is also why LND's verifyAllInputsSegWit rejects legacy inputs outright — "risk of malleability". A malleable input is a TXID that can move after we have committed to it, which is the same failure wearing a different hat.

I·4

No RBF on the funding transaction, ever. CPFP or wait.

Replacing the funding transaction changes the outpoints and destroys every channel in the batch. What enforces this is authorship, which is all that ever enforced it: only we can sign those inputs, and no code path in this repository builds a replacement.

replaceable: false is a statement of intent, not a defence. Measured against Bitcoin Core v29, the version this build develops against: mempoolfullrbf does not exist even as a hidden debug option, and getmempoolinfo reports "fullrbf": true with no way to turn it off. Full-RBF is unconditional, so a higher-fee conflict relays regardless of what our sequence numbers signal.

Which is why the verifier's sequence-number refusal was withdrawn, on 2026-08-26. Refusing a transaction over a signal that changes nothing is a lint wearing an invariant's clothes. plan.Code has no Replaceable member and checkInputs no longer looks at a sequence number — though InputView.Sequence still records what each input said, so the fact is on the report and simply not judged.

Removing it did not relax I·4, and the two are the same diff to a fast reader. The lint never held anything: it judged a signal the network ignores. What holds I·4 is authorship, and what catches a wallet that flips replaceability on is the I·3 txid pin, since changing a sequence number changes the TXID.

Your other wallet, holding the same keys, can build a replacement. The discipline lives in the human. See A batch that never confirms for the one case where that is the right thing to do, and the ordering that keeps it from losing funds.

Cost of I·1Setting no_publish on every channel also sets NoFundingTxBit (lnwallet/reservation.go:415), and that bit gates rebroadcastFundingTx (funding/manager.go:769) — so LND will not re-broadcast the funding transaction on restart. We inherit that duty. Publishing through WalletKit.PublishTransaction rather than bitcoind hands the transaction to LND's wallet-level rebroadcaster, which "will continually attempt to re-broadcast the transaction on start up, until it enters the chain", restoring the property by another route. The raw transaction is also kept in the run journal.

Precisely: NoFundingTxBit does not skip only the broadcast. It gates four things — the broadcast, the startup rebroadcast, the funding-input witness verification inside CompleteReservation (lnwallet/wallet.go:2275, which has no witnesses to check), and the transaction label. CompleteReservation, WatchNewChannel and the chan_pending emission are untouched, which is exactly what I·1 needs.

Sequencenine steps

What the app actually drives

The interactive lncli prompts exist only because the CLI is interactive. Underneath is a plain gRPC state machine, fully scriptable, and the client generates the identifiers — so the app owns every handle from the first call.

Read the gate row first. Everything above it is reversible at no cost; everything below it happens with every channel already recoverable. That line moved, and moving it is what this revision is about.

Each address is printed on a line of its own. A P2WSH funding address is 62 characters and the pane is 78, so a label column wide enough to read pushes it past the edge — and a wrapped address is one an operator has to reassemble by hand at the one step where a wrong character costs a channel. Alone on a line it is also one double-click to select.

A PSBT skeleton was considered and rejected: Sparrow signs PSBTs, it does not fund them. There is no "load this unfunded PSBT and choose coins for it" flow outside Core's walletcreatefundedpsbt, and removing Core is the point.

"Do not sign yet" is enforced, and it is I·1 Step 4 is the one moment left where the gate can be defeated from outside. The operator has a funded transaction and nothing has reached chan_pending, so a signature here means somebody is holding a broadcastable funding transaction with no channel recoverable — and a wallet's Broadcast button is two clicks from its Sign button. A transaction that reached the network at that moment would confirm one 2-of-2 output per channel with no channel behind any of them, which is the outcome the whole sequence is arranged around.

So a packet arriving here with any signature on it — a partial or a complete witness — is refused, by combine.Unsigned, before psbt_verify is called. The cost is building the transaction again inside clock A. Everywhere after step 6 the opposite is true: a complete witness is what step 7 is asked for, because by then a wallet holding signed bytes front-runs nothing.

That asymmetry is why step 7's second encoding is not shared with step 4. Step 7 reads a finalized raw transaction as well as a PSBT; step 4 reads a PSBT and only a PSBT, because combine.Unsigned refuses by reading a packet's partial signatures and a raw transaction does not have any to read. Relaxing the one sniffer both steps used would have taught step 4 to accept, in silence, the exact packet the paragraph above exists to refuse. So the acceptance sits at step 7's call site, in combine.SignedFromTX, and nowhere either step could reach it by accident.

This page used to reject skip_finalize, and the reason it gave was false The previous revision said skip_finalize "skips the very step that produces the chan_pending gate", and called that non-negotiable. It does not skip the gate. In lnwallet/chanfunding/psbt_assembler.go:293-300, PsbtIntent.Verify ends by closing PsbtReady itself when !i.shouldPublish && skipFinalize — setting FinalTX to the unsigned transaction and the state to PsbtFinalized — and funding/manager.go:2314 reads that channel with a bare case nil:, commented "Nil error means the flow continues normally now."

What it actually skips is handing LND a signed transaction, which lnwallet/wallet.go:1900 only stores when ShouldPublishFundingTX() is true. With no_publish set — which I·1 requires anyway — LND never needs a signature. CompileFundingTx still runs (:1881) because it "sets the actual funding outpoint in stone", and the unsigned transaction suffices: every input is segwit, so witnesses cannot move the TXID.

The dangerous combination is unreachable, twice over. PsbtFundingVerify checks skipFinalize && ShouldPublishFundingTX() before it touches the intent and returns "cannot set skip_finalize for channel that did not set no_publish" (lnwallet/wallet.go:764) — confirmed on a running node, in those words. The app does not lean on that: it asserts no_publish on its own side of the wire before sending, because the combination it prevents would be a request to arm a channel and broadcast, and having the only guard for that live in somebody else's codebase is not a design. Because LND checks before advancing, a stream refused this way is untouched and its shim still cancels — which is what makes a batch refused at step 5 re-armable rather than lost.

One consequence: there is no psbt_finalize call anywhere in this build. Verify leaves the intent in PsbtFinalized, and both of LND's finalize entry points require PsbtVerified, so the call would be refused with "invalid state. got finalized expected verified". Step 6 reads the streams; it does not step the machine.

Proved on regtest, 2026-08-25. Two streams opened with psbt_shim and no_publish, an unsigned batch transaction, psbt_verify with skip_finalize on each — and both channels reported chan_pending at exactly the outpoints the funding addresses resolve to in the unsigned transaction, with the mempool clear, in under a second. Nothing in that test signs anything; the absence is the assertion.

Still a deliberate omissionbase_psbt chaining, which LND documents as a way to accumulate outputs across sequential opens. Its old rejection was "we build the transaction ourselves", and that is no longer true — Sparrow builds it. The reason that survives is better: chaining makes LND the assembler, so there is never a single moment at which the whole output set is checked against the whole plan. Our verifier checks all n outputs at once, which is what catches a swapped, missing or duplicated one. Chaining defeats the check this tool exists for.
Constrainttwo clocks

They have different owners and different consequences

An earlier revision of this page conflated these into "the ten minutes". They are not one clock, and the dangerous one is not the one anybody watches.

A

Ten minutes — the peer's

steps 2 → 6

Our node never expires a PSBT reservation. pruneZombieReservations skips them outright — "these reservations are always initiated by us and the remote peer is likely going to cancel them after some idle time anyway" — so the only clock is the peer's, and it stops at chan_pending, when the reservation completes.

margin — the whole window, unspent
0:002:004:006:008:0010:00
Steps 2–6 — measured at 0.55 s for n = 2 Formerly: the signing round

That sliver on the left is the point of the whole revision. The previous design put a cold-storage signing round inside this window and spent a phase model, a dress rehearsal and a 5:00 abort gate on making it fit. With skip_finalize the window contains no signing at all — only RPCs — so the machinery that defended it is gone, along with the reason for it.

What blowing clock A costs: a restart. Nothing was broadcast and nothing was signed, so re-arming is free. Where the ten minutes are actually spent is step 4, in Sparrow, before anything has been shown to LND — so a lapse there is n shim cancels and nothing else. Past step 5 the question changes rather than the cost: psbt_verify with skip_finalize completes LND's funding flow instead of parking it, so a stream that verified is one whose channel LND has probably created, and the teardown for it is an abandon. Which of the two a given stream needs is decided by asking PendingChannels, not by assuming. Ten minutes is LND's default — chanfunding.DefaultReservationTimeout, checked by a sweeper on lncfg.DefaultZombieSweeperInterval = 1 minute, neither adjustable in a release build, so a peer holds one for at most 11 minutes. Measured against the harness at 10m41s under lnd v0.19.3-beta and again at 10m14s under v0.21.2-beta — the spread is the sweeper's one-minute granularity, not a moved timeout. A CLN or Eclair peer has its own, and any peer can reconfigure it: design against this as a convention, not a guarantee.

B

About 2016 blocks — also the peer's

step 6 → confirmation

Roughly two weeks. waitForTimeout counts lncfg.DefaultMaxWaitNumBlocksFundingConf from the channel's broadcast height, and fundingTimeout fires — "only returned for the responder" (funding/manager.go:2940). The peer marks the channel cancelled and forgets it. We never do.

Blowing clock B is worse than blowing clock A, and it is the one nothing draws attention to. Clock A expiring costs a restart. Clock B expiring means the peer has deleted their state — and a funding transaction that confirms afterwards leaves this node holding coins in a 2-of-2 with a counterparty who no longer knows about the channel. Only a force-close gets out of it, and only because the commitment signature was stored at step 6.

So the recovery output names clock B in blocks — "peers give up at block 887,412, about 13 days" — rather than saying there is time. PendingChannels publishes the countdown as funding_expiry_blocks; the app watches it and warns long before it is urgent.

Verifierrefuse vs report

The difference between a tool and a nanny

The app does not build your transaction, so most of what it could complain about is none of its business. The split is what it will stop for, and what it will merely tell you.

Refuses

The transaction does not match the plan you approved, or an invariant is broken. UnnamedOutput, MissingOutput, DuplicateOutput, WrongAmount, LegacyInput (I·3, and LND's own requirement), DuplicateInput, MismatchedUTXO, NoUTXOInfo — and the TXID pin at step 8.

Reports

Your fee and change arrangements are yours. ChangeMissing, ChangeTooSmall, FeeTooLow, FeeTooHigh. A batch with no change output has no CPFP lever and therefore no exit but an out-of-band double-spend — worth saying, and not worth refusing over.

Where they landed, and why not where this page first saidBuilt on 2026-08-26. This page used to say the four would move to the existing Verification.Unchecked list. They did not. Unchecked names what the verification could not establish, and it renders under the heading "Not checked here" — but "your change is 600 sat and the floor is 12,350" is something the verifier plainly did establish, and filing it there would have cost that heading the only thing it is for. So Verification grew a third list, Reports []Finding, rendered under "Reported, not refused", and OK() is still len(Problems) == 0.

Finding is a separate type from Problem rather than the same one in a second slice, because Problem's own comment — "Every problem is a refusal. There is no severity here on purpose" — had to stay literally true rather than be edited around. Two types make the split something the compiler knows, so a demoted finding cannot reach Problems by accident and OK() cannot come to depend on a grade somebody set wrong. Nothing grew a severity field.

Both screens that print a verification print the reports. Step 5 prints its report unconditionally; step 7's recheck prints nothing on success, so it prints the reports on their own — the size is exact there rather than an upper bound, so a rate that sat inside tolerance at step 5 can land outside it at step 7, and a report nobody prints is worse than the refusal it replaced. A batch with no change output now arms with no further prompt, which is the point rather than a gap: a tool that refused your transaction over your own change arrangements would be claiming an authority it gave up at step 4.

Two consequences of the app no longer selecting coins. It cannot size a change output for you, only tell you yours is too small. And nothing pre-excludes a legacy coin any more — Sparrow picks the coins, so LegacyInput at step 5 is the first thing that notices, which is why it stays a refusal rather than joining the reports.

Which output is the change, now that the app does not choose it Not named — recognised. The plan cannot name a script it never derived, and an output the plan does not name is an UnnamedOutput refusal, so without an answer here the verifier would refuse every transaction Sparrow builds. plan.RecogniseChangeIn reads the master key fingerprints off the transaction's own inputs — those are the wallet that is about to sign — and accepts an output carrying those same fingerprints on derivation branch 1. That is the evidence a hardware signer uses to decide an output is its own change rather than a payment, and plan.Change.Recognise already existed for it.

It is weaker than naming the script, and the report says so — such an output renders as "recognised by key origin rather than by address". The packet gets to nominate its own change output, and the circle is deliberately small: the funding outputs are checked by script and to the satoshi against addresses LND issued, so nothing here can move a channel's money, and a wallet that lies about its own change address has already taken the coins it is about to sign for.

run --change ADDRESS names the script instead, which is the stronger check, and it is the answer for a wallet that writes no key origins at all — that case is a refusal saying which of the two to supply, rather than a plan reported as broken.

Commissioningproving it once

The state machine, tested on mainnet, at zero cost

Regtest proves the code path. It cannot prove these peers, this node and this wallet, and no harness substitutes for that. So we lean on the property that already governs this design: nothing is at risk until broadcast. Every step short of publishing can run against mainnet, against real peers, with real coins that never move.

I·1 makes this sharper than a test mode. Because no_publish is set on every channel in the production flow, the probe is not a separate code path — it is the real run with the final action withheld. Composing it forced exactly one branch, an if before the publish call; everything above that line runs unconditionally, and the type system carries the rest of the argument. Publish takes a value carrying one chan_pending receipt per channel in an unexported field that only the gate fills, and it re-derives the TXID from the bytes it is handed and refuses any that do not hash to the one LND pinned. That used to be the raw transaction in the unexported field; after the inversion the transaction arrives from outside, so the unforgeable thing had to become the receipts.

C

Cold probe

run once per setup

Steps 1 through 7 exactly as production runs them. Step 8 is simply not taken.

  1. Open the streams, print the plan, build a genuine transaction in the real wallet, and verify it.
  2. Watch every chan_pending arrive and confirm the gate at step 6 closes as expected — this is the assertion the whole safety argument rests on, and it now happens with nothing signed.
  3. Export the channel backups, verifying that step works on pending channels.
  4. Sign it for real, so the devices and the descriptor are exercised, and confirm the TXID has not moved.
  5. Stop. Then clear up, which the run does itself rather than suggesting: AbandonChannel for each pending channel — expect pending_funding_shim_only to be refused and the blunt flag to be asked for, which is the normal route here and not a warning sign — and shim_cancel for any stream that never verified.
  6. Separately, deliberately let one stream lapse without verifying, to observe the peer timeout for real rather than trusting the ten-minute figure.

Cost: nothing on-chain. No fee, no footprint, and the coins never move.

It is not free of the peers, and that is the thing to plan around. Every channel in a probe reaches chan_pending and is then abandoned — and AbandonChannel touches only our own database. The peer, as responder, keeps its side pending until fundingTimeout fires, DefaultMaxWaitNumBlocksFundingConf = 2016 blocks from the channel's broadcast height, about a fortnight. Nothing shortens it and nothing tells the peer otherwise. So a probe spends one of each probed peer's pending-channel slots for roughly two weeks — and against a peer running LND's default --maxpendingchannels=1, probing a peer and then opening a real channel with that peer are a fortnight apart. Decide which peers to spend before running it; --maxpendingchannels is not in gossip and cannot be read.

This paragraph used to say the only externality was "a briefly held reservation on each peer, which their own timeout clears". That is the cost of a shim probe — about eleven minutes — and not the cost of this one, which reaches chan_pending on every channel. The two draw on the same --maxpendingchannels budget and differ by two orders of magnitude.

The remaining exposure past the broadcast line is settled by making the first live run a deliberately small one — two channels at the smallest size the chosen peers accept — treated as commissioning rather than as a real allocation.

Consequence for the build orderThe abort and recovery paths must be working before the first mainnet probe, since the probe's normal termination is the abort path. That inverts the usual order: shim_cancel and AbandonChannel ship first, and the happy path is built on top of them.
Which abandon flagTry pending_funding_shim_only first: it refuses unless the channel is both shim-funded and pending, so it structurally cannot touch a confirmed channel. It refuses every channel this app opens. rpcserver.go:3344 infers "shim funded" from ThawHeight > 0 — there is a standing TODO about storing the funding type properly — and a plain PSBT open carries no thaw height, so the safe flag rejects with "channel … is not externally funded or not pending" on the ordinary path. Confirmed again on the new sequence: channels that reached chan_pending via skip_finalize are refused the same way. So the fallback to i_know_what_i_am_doing is the standard route, which moves the burden of safety off LND's flag and onto ours: before escalating, the app re-establishes the missing half of the check itself by asking PendingChannels. If the channel is not pending it refuses outright and offers no confirmation, because there is nothing a human could usefully authorise there.
Architecturecomponents

Where the pieces live

The trust boundary is the design's most important line. The app holds a narrow LND macaroon; it never holds key material, it opens no listening port, and it makes no outbound connection except to your LND.

Note what carries the PSBT: a file. The app writes none and reads two — --psbt FILE at step 4 and, at step 7, either FILE-signed.psbt or FILE-signed.txn beside it — both watched, because step 7 takes a signed PSBT or a finalized raw transaction and a wallet saving the latter names it .txn. The second name is derived rather than asked for, so it can never be given the unsigned file's value. Sparrow is on the same desktop as the devices. No browser, no tunnel for the transport, no file sync, no shared mount, no extra daemon. Bitcoin Core does not appear at all.

It refuses a --psbt path that already exists, and that is a rule rather than caution: the funding addresses the transaction pays to did not exist before the run — LND issues them at step 2 — so a file that predates the run cannot be this batch's transaction, and reading one would arm a batch against somebody else's outputs and find out at step 5. The check is made before LND is dialled, where a refusal costs nothing at all.

One transport, one contract

The contract is BIP174: any wallet that round-trips a PSBT works. Binary or base64, settled by the magic bytes. At step 7 a finalized raw transaction is read too — hex or binary — because that is what Sparrow's View Final Transaction hands over and what lncli is fed at the equivalent prompt; the base PSBT already holds everything the verifier reasons about, so the signed side need only carry the witnesses. In-house animated QR is deliberately out of scope; a QR-only signer is reached through a desktop wallet that already does it.

Resumable by default

SQLite records each pending channel ID against its funding outpoint, and the raw transaction — written before the call it describes, so a crash mid-publish leaves artifacts rather than mystery.

One front end, on purpose

An interactive CLI with one countdown line. Not a TUI: the only thing wanting live redraw is clock A, everything else is prose the CLI already renders, and a second renderer is a second place for copy to be wrong.

Commissioning without a testnet

A regtest harness covers the failure branches, but it is not what vouches for the funding flow. The state machine is proven on mainnet with real peers and zero on-chain cost, by exercising every step up to but excluding broadcast.

What the harness still needs that the app does notThe application drops Bitcoin Core, but a regtest test still needs something to build and sign a funding transaction — something to play Sparrow's part. Core's wallet is the natural stand-in, so the Core client and the simulated multisig cold wallet survive inside the harness. That is not a back door for an app-builds-the-transaction mode; it is the test fixture playing the operator.

Validating peers without asking anyone

All of it can be done through LND, and most of it without touching the network at all. Three tiers of certainty:

CheckSourceCost
Pubkey is well-formedLocal: 33 bytes, compressed, a real point on secp256k1None — catches typos and truncation instantly
Node exists; alias, addresses, channel count, total capacityGetNodeInfo — reads LND's own gossip graph, not the networkNone. Also lets the plan show a name instead of a hex blob, which is its own error check
Plausible channel sizeThe capacities of that node's existing channels, from the same local graphNone. The smallest and median capacity are a good empirical proxy for what they accept
Authoritative minimum, reserve, HTLC limits, accepted commitment typeA shim probe: open the stream and read accept_channel, or read the rejection text — peers do state their minimum in itFree only when it is refused. A probe the peer accepts holds one of its pending-channel slots for about eleven minutes — see below

There is no gossip field for "minimum channel size" — it is enforced conversationally, in accept_channel. So the only authoritative check is to ask, and third-party Lightning explorers stay out of the picture entirely.

The probe is not freeReading handleFundingOpen in order: the peer counts its live reservations for us plus its pending channels with no thaw height, and refuses with ErrMaxPendingChannels if that count already reaches --maxpendingchannels — LND's default for which is 1. Only after every limit check does it call InitChannelReservation and send accept_channel. So the cost splits in two, in opposite directions. A probe the peer refuses costs nothing at all: no reservation is created, so probing downwards to find a peer's minimum is free however many times you do it. A probe the peer accepts costs one of that peer's pending-channel slots, and shim_cancel does not give it back — CancelFundingIntent deletes an entry in our own wallet's map and sends the peer nothing. Only the peer's own zombie sweeper releases it.

So a run that probes all n peers and then opens collides with its own probes: against a peer running the default, step 2 is refused with "Number of pending channels exceed maximum", for a reason we created ourselves a minute earlier. Probe as a separate, earlier act, when a peer's minimum is genuinely unknown — then wait out the hold. A successful probe is step 2 with the answer thrown away.

One thing to know about reading the refusal: the peer's own words do survive, because failFundingFlow forwards the real text. They arrive under a claim that is not true, though. handleErrorMsg wraps every peer error in chanfunding.ErrRemoteCanceled when the reservation is a PSBT one, so a peer that refused in thirty milliseconds because the channel was too small arrives saying it "possibly timed out". Strip the wrapper and report what the peer actually said, alongside how long it actually took.

Hostingand configuration

One binary, one socket, no internet

A single static binary plus a SQLite file. It talks to LND over gRPC and has no other dependencies, no cloud component, and no listening port of its own. Run it on the LND box, or anywhere that can reach LND's gRPC port; if that means a laptop, the credential is copied there and that is the whole of the deployment question.

No sockets of its own. The rule is about who opens connections, not about keeping the batch hermetic — LND is a network node and will talk to peers, which is the point. What the app must never do is contact a third party: peer facts come from LND's local gossip graph, never from a block explorer, a fee API, or a Lightning explorer. Amounts, peer sets and timing are exactly the things those services log.

Configuration

Two files, deliberately separate. winthistle.toml holds connection details and never contains a secret, only paths to them. The batch file is where the money is: peers, amounts, and what each channel will charge to route. The plan is the reviewable artifact built from the two of them plus what only LND can supply — the funding addresses and the reserve top-up. It is what step 4 is typed against and what step 5 checks.

[lnd]
address      = "127.0.0.1:10009"
tls_cert     = "~/.lnd/tls.cert"
macaroon     = "~/.lnd/winthistle.macaroon"   # baked, not admin

[journal]
path         = "~/.winthistle/runs.db"

[fees]
target_sat_per_vb = 12.0            # no default, on purpose

There is no allow_rbf key, and writing one is refused rather than ignored. A key that appears in a config file and changes nothing is worse than no key at all, because an operator who sets it to true and watches the run proceed will reasonably conclude it was honoured. I·4 is enforced by authorship and nothing reads a preference about it, so the reader refuses the line and says why.

Every unknown section and every unknown key is refused, naming the line. That is not pedantry: the file is read once, at the start of a run that may end with a cold wallet on the table, and a misspelled key that silently defaults has told the operator nothing. It also means removing keys is a loud breaking change for anyone with a config file, which is the correct direction to fail in.

So a key that is removed says what happened to it. "[fees] has no key mode" reads like a typo rather than like the change it is, and the alternative — leaving a dead key in — is the thing this page calls worse than no key at all. The reader keeps a list of retired keys and sections, each with a sentence: [bitcoind] says the tool dials no Bitcoin node and what it used Core for; [limits] abort_after_signing_seconds says the window it bounded no longer contains a signing round. The entry goes in with the removal, or the refusal is the shrug.

Where the fee rate comes fromThe operator, and nothing else asks. It came from Core's estimatesmartfee until Core was removed, and the no-third-party rule above forbids the obvious substitute — a fee API is handed the size of what is being built and the moment it is being built, which together are most of what this tool exists not to leak. The options were to ask, to derive something from LND's relay floor, or to drop the fee finding; asking won, and not only by elimination. The app does not build the transaction and does not choose the fee, so what the verifier needs is not an estimate but something to hold the built transaction to — and the rate the operator declared is a stronger thing to check against than a number fetched on their behalf. It is also the shape of everything else here: you declare the batch, it checks the transaction. A rate that quietly became zero was never on the table: the config reader refuses a missing target_sat_per_vb, and the plan builder refuses a non-positive target, independently.

Setup the tool checks itself

A written guide is necessary and will rot. So the guide is short and the tool carries the checks: winthistle doctor tests every prerequisite in turn — LND reachable, the macaroon sufficient for each method it will call, peers resolvable in the graph, the run journal readable — and for each failure prints the exact command that fixes it rather than prose describing it.

The macaroon is the case where that matters most, because the required permission list is a property of the code. So the tool generates the baking command from its own method registry. The list printed on this page is illustrative; the one the tool prints is authoritative, and it cannot drift from what the code does. "Cannot" is doing work there: the client refuses at dial time to call a method the registry does not list, and a test type-checks the whole module and fails if the registry and the call sites disagree in either direction.

The credential is checked by asking, not by calling. The obvious way to find out whether a macaroon authorises a method is to invoke it, and for most of this list that is a bad idea: the interceptor runs before the handler, so a refused method costs nothing, but an allowed one runs, and AbandonChannel and PublishTransaction are not things to try with junk arguments to see what happens. CheckMacaroonPermissions answers directly — it examines the macaroon in the request rather than the caller's, runs the same check the interceptor would, and reaches no handler.

That also checks the half nothing else could: the never-list. The registry promises the credential cannot send coins, close a channel, sign a message or widen itself, and that is a promise about the file in the operator's config rather than about this build's intentions. An operator who points the tool at admin.macaroon has broken every part of it while everything still works, so doctor asks LND whether the credential holds onchain:write and the rest, and fails if it does. One warning about the two refusals that look alike: a credential that does not authorise a method is reported as InvalidArgument, while the interceptor refusing the caller arrives as an untyped error — a plain errgo error with no gRPC status attached, so it is codes.Unknown carrying the text "permission denied". Matching on the code alone confuses them; so does matching on the text alone.

The journal is the one piece of state worth backing up — it holds each run's pending channel IDs, funding outpoints and the raw transaction, which is what makes a crashed run recoverable rather than mysterious. It contains no key material. There is no version table and no migration machinery: the schema is one CREATE TABLE IF NOT EXISTS block, and it grows by new tables rather than new columns.

Recoverywhen it goes wrong

One question decides everything

Under pressure the only thing that matters is whether the transaction reached the network. The app answers that from its own journal, and then offers exactly one path.

Has the funding transaction been broadcast?
No — nothing is at risk, and nothing has cost anything. Cancel every shim with shim_cancel, abandon any channel that reached pending, and either start again or walk away. No on-chain footprint, no fees. Because of I·1 this covers every failure before the gate, which is every failure the batch is actually likely to have.
Yes — then all n channels reached chan_pending before it went out, because that is the only condition under which the app will publish. Every channel therefore holds its peer's commitment signature and every outpoint is watched by the ChainArbitrator. Three ways this ends, all of them solvent: the transaction confirms and the channels open; a peer vanishes and a force-close recovers the funds; or our own node is lost and the exported backup plus the peer's data-loss protection recovers them.

The order in that table is the new one, and the code now writes itarmed before signing is the whole inversion, expressed as journal states: a channel at chan_pending with nothing signed is the ordinary mid-run state rather than an edge case. It used to run the other way round, because the old sequence signed inside the peers' ten minutes and collected the receipts afterwards. Two consequences of the swap are worth knowing. An armed run with no raw transaction on disk is normal, not a contradiction — the bytes reach the journal immediately before the publish call and nowhere else, so their presence means "we may owe a rebroadcast". And the gate is a count rather than a state: MarkPublishing asks how many channels are at chan_pending instead of trusting that armed is the state before it, because signing now sits in between.

One window this leaves open, unchanged in kind and in size from the old sequence. A process that dies between a channel's psbt_verify and its receipt leaves a row saying verified for a channel LND has probably already created. Inside a run that cannot happen — the receipt collector asks PendingChannels whenever a receipt does not arrive, and journals what it finds — but a crash never gets to ask, and the shim cancel that follows reports success for a channel that is still pending on the peer's side until clock B runs out. The pre-inversion sequence had exactly the same gap between psbt_finalize and its receipt.

Why publishing is written firstIt is the only ordering that fails safe. Written after the call, a crash mid-publish would leave a run the journal calls abortable, with a transaction that may already be relaying. Written before, the same crash leaves a run nothing will touch, which is the correct answer to "we do not know." The cost is that a publish refused by the node also lands here, and that is accepted: a broadcast that returned an error is not a broadcast that did not happen.
The branch that used to be hereAn earlier revision described a third outcome: published, but with a channel that never completed negotiation, whose output is a 2-of-2 with a counterparty who never signed — coins gone. This design has no path that reaches it, and it now takes only one invariant to say so rather than two. I·1 means the transaction is not published until every channel is already recoverable. That used to need I·2 beside it, because a signed transaction existed while the gate was still shut and someone else might have held it. Under the new sequence no signature exists until after the gate has closed, so there is no window for a second party to publish into. Remove I·1 and the branch comes back.

A batch that never confirms

This is the state the CPFP handle exists for, and it is worth naming exactly, because earlier drafts of this document described it in language that made it sound like a loss. It is not one — and the wrong framing was the dangerous part, because an operator who believes coins are at risk will reach, under pressure, for the one thing I·4 forbids.

Nothing is at risk while the funding transaction is unconfirmed. The coins are ours, unspent, in a transaction only we could have signed. Every channel reached chan_pending, which makes it recoverable by force-close once the funding transaction confirms — before that there is no channel yet, only a promise. So the cost of a stuck batch is the ceremony: the peers' cooperation and the run, to be done again. Under the new sequence that is cheaper than it was, because the signing round is no longer inside anybody's window.

But it cannot be abandoned, either. An unconfirmed funding transaction never becomes safe to abandon on its own: its inputs stay unspent, so it stays valid indefinitely, and eviction from mempools does not invalidate it. winthistle recover therefore refuses any run that reached the publish call — abandoning a pending channel whose funding transaction later confirms strands its funds with no force-close path, which is precisely LND's "DO NOT PUBLISH … OR THE FUNDS CAN BE LOST". A batch that never confirms leaves its coins frozen: not abortable, not safely spendable, waiting on the mempool.

That inverts what CPFP is for. It is not a speedup — it is the exit. Confirm the batch, then close the n channels normally if you no longer want them; that costs the funding fee plus n cooperative closes and is completely safe. Which is the correct way to read the advice about change outputs: not insurance against slowness, but what keeps a batch from having no way out at all.

The freeze is a thin tail: it needs the fee market to move further than you allowed for, while WalletKit re-offers the transaction on every restart. And it is not a state CPFP can rescue after the fact — a child of an absent parent is an orphan. What a child can address is a parent sitting in a mempool and confirming too slowly.

This is why a change output is worth having, and why it is advice rather than a gate. Without one there is no lever at all and the only route out is the procedure below. With one, the exit is ordinary. But the app no longer builds your transaction, so it cannot size a change output for you — it can only tell you that yours is small enough to cost you this, and let you decide. A tool that refused your transaction over your own change arrangements would be claiming an authority it gave up at step 4.

The one route out, which this build does not take If a batch is frozen and waiting is unacceptable, the only way to release the coins is to double-spend one of its inputs — and this build will not do it for you. Not because the operator cannot be trusted with it, but because building one would put a funding-transaction replacement in the codebase, and I·4 is a statement about what this program contains. The line is authorship, not knowledge: we can say what the only way out is, and still refuse to be the thing that does it. What the app does give you is the material: recovery names the inputs and the txid.

The procedure, and the ordering that keeps it from losing funds:

  1. Do not abandon anything first. Every channel's state — including each peer's commitment signature — is what lets you force-close if the original confirms after all. Abandoning before the replacement is settled is the one move that turns a frozen batch into a lost one.
  2. Build and broadcast a transaction, with your own tools, spending at least one of the funding transaction's inputs back to your own wallet. Full-RBF is unconditional in Core v29, so it will relay despite the original's replaceable: false.
  3. Wait for it to be deeply confirmed. Until then both transactions are live and you cannot know which wins. There is no signal that resolves this faster than confirmation depth.
  4. Only once the original is unmineable — every one of its inputs spent by a confirmed transaction — abandon the pending channels.
  5. If the original confirms instead, you have channels rather than coins. Close them; if a peer has passed its ~2016-block horizon and forgotten, force-close, which works because of step 1.

The honest summary is that the safe version of this procedure is slow enough that it is rarely better than waiting. Which is the argument for keeping a change output and for sizing it against a pessimistic target rather than a hopeful one — an argument worth making to the operator, in the report, rather than enforcing over their head.

Claimsverify first

What is evidence, and what is not

Each of these is load-bearing, and none should be taken on faith from documentation, including this document. settled in source means read out of LND's source — better evidence than prose, but not a passing test. proven on regtest means there is one. The cold probe passed on 2026-08-26, so the sequence as a whole is settled on mainnet too: two real peers, both to chan_pending with nothing signed, backups exported off pending channels, the TXID unmoved at step 7, step 8 withheld, and a teardown that left nothing behind. The badges below still say what established each individual claim, and most of them are still regtest and source.

  • proven on regtest Does skip_finalize with no_publish reach chan_pending over an unsigned transaction? Yes — this is the finding the whole revision rests on. Two streams, an unsigned batch transaction, psbt_verify with skip_finalize, and both channels reported chan_pending at exactly the outpoints the funding addresses resolve to, with the mempool clear. PendingChannels listed both, which is the same fact by a route that does not depend on the stream: a channel in that list was put there by CompleteReservation, the call that stores the peer's commitment signature. Nothing in the test signs anything, and that absence is the assertion.
  • proven on regtest Does the I·1 gate hold for a whole batch? Yes, observed at n = 3: three chan_pending receipts against one transaction, one shared TXID with three distinct output indices, and the mempool checked after every step including the last — precisely where LND's own "all but the last" idiom would have broadcast. Then published once, confirmed, and all three channels opened.
  • proven on regtest Does shim_cancel still succeed after a successful psbt_verify? Yes while the reservation is still open, and that is narrower than it sounds now. On the old sequence psbt_verify only attached a verified packet to the intent, so the intent was always still there to cancel. With skip_finalize the same call completes the funding flow, and CompleteReservation deletes the intent — so cancelling works for a stream whose peer has not answered, and a stream whose channel armed needs an abandon instead. The app decides between them by asking PendingChannels whenever a receipt does not arrive. What is still true is the thing that made clock A cheap: the ten minutes are spent at step 4, before LND has been shown anything, and a lapse there costs n free cancels.
  • proven on regtest Is pending_funding_shim_only usable as the abandon flag? No, and this is settled twice over. It refuses every channel this app opens, on the old sequence and on the new one, because LND infers "shim funded" from a thaw height a plain PSBT open never sets. The blunt flag behind an explicit confirmation is the standard route.
  • settled in source Who owns the ten-minute clock? Not us: pruneZombieReservations skips PSBT reservations outright, so our node never expires one. On the peer it is set at the end of the same handler that sends accept_channel. The timeout is DefaultReservationTimeout = 10 minutes, swept on a 1-minute interval, neither adjustable in a release build. Measured on regtest at 10m41s under lnd v0.19.3-beta and at 10m14s under v0.21.2-beta — ten minutes plus sweeper granularity both times, as predicted. What the operator sees is "remote canceled funding, possibly timed out"; the "possibly" is ours, and the peer does not say it timed out.
  • settled in source What does RequiredReserve return for private channels, given the field is named additional_public_channels? It has no idea whether the channels you name are public, so the caller must pass the count of announced members only. Private channels are invisible to the check twice over: the counter skips them, and the enforcement returns early when the channel being opened is unannounced.
  • proven on regtest Will UpdateChannelPolicy accept a pending channel point? Neither yes nor no, and the real answer is worse than both: the call does not fail. It returns success with the refusal inside it, as UPDATE_FAILURE_PENDING / "not yet confirmed" in failed_updates, with a nil error. A caller that checked only the error would record a policy it had never applied and go on forwarding at 1000 msat and 1 ppm believing otherwise. Every attempt has to be judged against failed_updates, and only an empty list is a success.
  • settled in source Can the initiator read a peer's minimum_depth? No. It is in accept_channel and in LND's stored channel record, and in no RPC. So step 9 observes it — the number of confirmations a channel has when it first appears is that peer's answer — and the design must not promise "usable after k confirmations" up front. It is authoritative, it arrives far too late to plan with, and it is exactly the right thing to record for the next batch.

Later the same day the fee and change findings became reports rather than refusals and the sequence-number refusal left the verifier, which were the last two things this page was ahead of. It is no longer ahead of the code. And the one thing left that was never a code change — the mainnet cold probe below, against real peers, with coins that never move — ran on 2026-08-26 and passed. Three attempts failed before it, none of them on the safety model: one unattended, one on clock A, and one on the signed file being a raw transaction the transport would not yet read.

Deleted, in one slice: Bitcoin Core (the fee estimate and testmempoolaccept), the watch-only wallet setup, the dress rehearsal, the multi-device signing round, the CPFP child and the local web UI. About 28,000 lines. The fee number is declared by the operator now; the pre-flight is not replaced, and plan.Verify's "not checked" list says so, naming node policy — min relay fee, standardness, ancestor limits — as what is lost and testmempoolaccept as the thing that would have answered it. What survives is narrower and is not nothing: every input's witness is executed against its own script before the transaction is published.
