Channel Opener

Premisewhat this replaces

The work is coordination, not cryptography

The manual process works. What makes it arduous is that a human is holding the state machine in their head: which pane is which peer, which prompt wants base64 and which wants raw hex, which pane has --no_publish, how much reserve LND will demand once the new channels exist, and how many of the ten minutes are left. Every one of those is mechanical, and every one of them is a place to lose a channel — or, in the worst case, coins.

So this tool owns the state machine and the clock, and hands the human back exactly two jobs: approve the transaction and sign it. Nothing else should require a decision under time pressure.

ScopeOne LND node, one funding transaction, n channels, funded by an external single-sig or m-of-n wallet whose keys never touch this machine.
Invariantsload-bearing

Four rules that shape everything else

These come from LND's own protocol constraints, not from preference, and each is enforced in code as a gate rather than documented as advice. The first one is the reason this tool can claim that no channel in a batch is ever left unrecoverable.

I·1

Publish only once every channel is already recoverable.

LND's "DO NOT PUBLISH" warning is about ordering, not authorship. The condition that actually matters is that the transaction must not reach the network before every channel has received its peer's funding_signed — the counterparty signature on our initial commitment transaction, which is precisely what lets a force-close recover the funds.

In funding/manager.go, chan_pending is emitted strictly after CompleteReservation(nil, commitSig) has stored that signature and after WatchNewChannel has handed the outpoint to the ChainArbitrator. So n chan_pending events is exactly the safe condition — and we gate on it: no_publish is set on every channel, not all but the last. Once all n report pending, we publish. There is no ordering in which the transaction can reach the network while any channel is still unrecoverable, because we hold the only copy of it until the gate opens.

I·2

The app holds the last signature.

I·1 is only true if nothing else can broadcast. A fully-signed transaction is a bearer instrument: any party holding one can publish it, buggily or maliciously, before the gate opens. So signers return partial signatures, and combining and finalizing happen in-app — no external device ever possesses a broadcastable transaction. For m-of-n this falls out for free. For single-sig it cannot, since the lone signer necessarily produces a complete transaction; there, a genuinely air-gapped signer with no network path is a requirement rather than a preference.

I·3

The TXID must not move after verification.

LND commits to the funding outpoint at psbt_verify: "no inputs or outputs can change, only signatures can be added. If the TXID changes between this call and the publish step then the channel will never be created and the funds will be in limbo." A signer that re-selects coins or re-derives change silently breaks the batch, so the app hashes the verified transaction and refuses any returned PSBT whose unsigned TXID differs, naming the device that did it.

This is also why LND's verifyAllInputsSegWit rejects legacy inputs outright — "risk of malleability". A malleable input is a TXID that can move after we have committed to it, which is the same failure wearing a different hat.

I·4

No RBF, ever. CPFP or wait.

Replacing the funding transaction changes the outpoints and destroys every channel in the batch. A stuck batch can only be accelerated by spending its change output. Therefore: always include a change output we control, sized large enough to pay for a meaningful child, and disable replaceability in the UI entirely.

Cost of I·1Setting no_publish on every channel also sets NoFundingTxBit, and that bit gates rebroadcastFundingTx — so LND will not re-broadcast the funding transaction on restart. We inherit that duty. Publishing through WalletKit.PublishTransaction rather than bitcoind hands the transaction to LND's wallet-level rebroadcaster, which "will continually attempt to re-broadcast the transaction on start up, until it enters the chain", restoring the property by another route. The raw transaction is also kept in the run journal so we can re-broadcast independently.
Sequencethe funding flow

What the app actually drives

The interactive lncli prompts exist only because the CLI is interactive. Underneath is a plain gRPC state machine, fully scriptable, and the client generates the identifiers — so the app owns every handle from the first call.

Deliberate omissionLND documents skip_finalize as a shortcut for batch members, and base_psbt chaining as a way to accumulate outputs. We use neither. Chaining is an ergonomic crutch for the CLI — we build the transaction ourselves. And skip_finalize skips the very step that produces the chan_pending gate in step 8, which is the one thing this design will not give up.
Constraintthe ten minutes

Budgeting the window

An LND peer forgets a pending channel after roughly ten minutes, and LND's own docs concede there's no reliable way to know the deadline for a non-LND peer. With n parallel streams there are n clocks starting at slightly different moments, so the real budget is the earliest one. The app shows a single countdown: the minimum remaining across all streams.

Machine work inside that window is trivial — well under a minute for a realistic batch. Effectively the entire budget belongs to humans handling hardware. That reframing is what the phase model below is built on.

The 5:00 line is a hard gate, not a warning: if rehearsal showed a signing round-trip slower than five minutes, the app will not arm the batch. Note what running out of time now costs, though. Because nothing is published until the step 8 gate, a lapsed window strands no channels and spends no fees — it costs one more signing round. The clock is an inconvenience, not a hazard.

Modelthree phases

Move every slow thing outside the clock

The reason the manual process is stressful is that it begins the countdown before anyone knows whether the signing setup works. Splitting the run into a rehearsal, an armed window, and a settlement pass means the clock only ever covers work whose duration has already been measured.

0

Rehearsal

no clock running

No funding streams are open, so nothing can time out. Everything here is repeatable and free.

  1. Peer pre-flight. Connect to each peer; check min and max channel size, accepted commitment type, and minimum_depth. Show the user "usable after k confirmations" per channel, up front.
  2. Reserve arithmetic. Ask LND, don't guess: WalletKit.RequiredReserve(additional_public_channels = n), compare against the confirmed on-chain balance, and add a top-up output to a fresh p2tr node address for any shortfall.
  3. Lock the coin set and the fee rate. Segwit inputs only, confirmed inputs only, with a change output sized so a CPFP child could pay for itself.
  4. Dress rehearsal. Build a decoy PSBT — same inputs, same fee, outputs paying back to the cold wallet — and push it through every signer for real. Confirm each device produces a valid witness, combine and finalize it, run testmempoolaccept, then throw it away.
  5. Record the measurement. The rehearsal's wall-clock signing time becomes the gate on Phase 1.

This phase catches the two failures that cost the most last time: a signer that produces malformed witnesses, and a reserve shortfall discovered mid-window.

1

Armed window

countdown live

Steps 1–8 of the sequence above, with the countdown visible throughout. The transaction shape is already decided; only the funding addresses are new.

  • Re-arm is one action. If the window lapses, cancel every shim with FundingStateStep{shim_cancel{pending_chan_id}}, reopen the streams for fresh addresses, and re-issue the same transaction with the outputs swapped. Nothing has been broadcast, so nothing is lost — the cost is one more signing round.
  • Sequential fallback. If signers are too slow to batch at all, the app offers one channel per transaction. More fees, no atomicity, but it completes. Naming this as a supported mode beats discovering it at 9:30 on the clock.
  • Nothing else is clickable. During the window the UI shows the countdown, the signing tracker, and abort. No settings, no editable fields.
2

Settlement

until confirmed + active

The transaction is public and the channels are pending. Two things still need watching.

  • Close the fee-policy race. New channels sit at LND's defaults — 1000 msat base, 1 ppm — from the moment they go active. The app takes the channel point from each chan_pending, polls until the channel is active, and applies the intended policy via UpdateChannelPolicy immediately. Policy is chosen per peer back in Phase 0, so this needs no human at all.
  • Confirmation watch. Track depth against each peer's minimum_depth, and offer the CPFP child from the change output if the batch stalls. Never offer a replacement.
Commissioningproving it once

The state machine, tested on mainnet, at zero cost

Phase 0 opens no funding streams — that is exactly what makes it untimed, and exactly why it cannot vouch for LND's funding flow. Signers, descriptors and fee arithmetic are the things rehearsal proves. Everything in the sequence from step 2 onward is untested by it.

Rather than stand up a signet node for that, we lean on the property that already governs this design: nothing is at risk until broadcast. Every step short of publishing can therefore run against mainnet, against real peers, with real coins that never move.

I·1 makes this sharper than a test mode. Because no_publish is set on every channel in the production flow, the probe is not a separate code path — it is the real run with the final action withheld. There is no rehearsal-only branch that could behave differently on the day, and step 9 is the only line of code the probe does not execute.

C

Cold probe

run once per setup

Steps 1 through 8 exactly as production runs them. Step 9 is simply not taken.

  1. Open the streams, build and verify a genuine PSBT, sign it with the real devices, combine and finalize in-app, and confirm testmempoolaccept passes.
  2. Finalize all n channels and watch every chan_pending arrive. Confirm the gate at step 8 closes as expected — this is the assertion the whole safety argument rests on.
  3. Export the channel backups, verifying that step works on pending channels.
  4. Stop. Then clear up: AbandonChannel with pending_funding_shim_only for each pending channel, shim_cancel for any stream that never finalized, and release the Core UTXO locks.
  5. Separately, deliberately let one stream lapse without finalizing, to observe the peer timeout for real rather than trusting the ten-minute figure.

Cost: nothing on-chain. The only externality is a briefly held reservation on each peer, which their own timeout clears.

That covers most of the open questions. The two it cannot reach both sit past the broadcast line: whether UpdateChannelPolicy accepts a pending-but-inactive channel point, and the settlement path as a whole. The first is neutralised by making Phase 2 poll unconditionally instead of depending on the answer. The second is settled by making the first live run a deliberately small one — two channels at the smallest size the chosen peers accept — treated as commissioning rather than as a real allocation.

Consequence for the build orderThe abort and recovery paths must therefore be working before the first mainnet probe, since the probe's normal termination is the abort path. That inverts the usual order: shim_cancel, AbandonChannel and the UTXO-lock release ship first, and the happy path is built on top of them.
Which abandon flagUse pending_funding_shim_only, not i_know_what_i_am_doing. The former refuses unless the channel is both shim-funded and pending, so it structurally cannot touch a confirmed channel. One caveat from rpcserver.go: "shim funded" is inferred from ThawHeight > 0 — there is a standing TODO about storing the funding type properly — so it may not recognise a plain PSBT open with no thaw height. The app tries the safe flag first and only falls back to the blunt one on that specific rejection, with an explicit confirmation.
Architecturecomponents

Where the pieces live

The trust boundary is the design's most important line. The app holds an LND admin macaroon and Core RPC credentials; it never holds key material, and it is never exposed to the internet.

Note what carries the PSBT between the two machines: the browser. The UI is viewed on the desktop through the tunnel, so a download hands the PSBT to Sparrow and an upload hands it back — no file sync, no shared mount, no extra daemon. The topology most people already have turns out to be the transport.

Two engines, one safety model

With Core, the app builds the transaction itself and owns coin selection, change and fee rate. Without it, Sparrow builds and the app verifies. The LND sequence and all four invariants are identical either way — see below.

Resumable by default

A closed tab must never orphan a funding stream. SQLite records each pending channel ID against its funding address and output index, per-signer signature state, and the finalized raw transaction — written before the publishing call, so the artifacts survive a crash mid-publish.

Transport, not typing

Base64 in and out, file download and upload, and animated QR — BBQr and ur:crypto-psbt — with webcam capture on the return leg. This is the one place a browser UI is genuinely better than a terminal, and it is where multisig ergonomics are won.

Commissioning without a testnet

No signet or regtest harness. Instead, the state machine is proven on mainnet with real peers and zero on-chain cost, by exercising every step up to but excluding broadcast. See Commissioning below — that mode is a first-class part of v1, not a debug affordance.

Two engines

Requiring a fully-synced, unpruned Bitcoin Core is the heaviest thing in the prerequisites, and for a lot of otherwise well-run nodes it is a blocker — Umbrel and friends often prune by default, and a descriptor import needs blocks a pruned node has thrown away. So Core is optional, and the difference between the two modes is convenience, not safety.

Directed — with CoreAssisted — without

In assisted mode the app emits a batch plan — every funding address with its exact amount, the reserve top-up, a target fee rate and the input constraints — and then verifies what comes back, output by output: each funding script present exactly once at exactly the right amount, no outputs to scripts the plan does not name, fee rate within tolerance, every input segwit and confirmed. That check is strictly mechanical and it is the same check LND's own psbt_verify will repeat at step 5.

On losing testmempoolacceptLess of a loss than it sounds. Executing every input's script locally against the witness data in the PSBT answers the question we actually care about — will each input validate — more directly than a mempool acceptance test does, and needs no chain data. What testmempoolaccept adds on top is node policy: min relay fee, standardness, ancestor limits. Worth having, and worth a warning when it is unavailable, but not load-bearing.
Where assisted mode is genuinely weakerI·2 says no external party ever holds a broadcastable transaction. In assisted mode Sparrow builds and signs, so the operator must stop short of Sparrow's own broadcast button. For m-of-n that resolves cleanly: let Sparrow apply m−1 signatures and have the app collect the last partial, and Sparrow never holds a complete transaction. For single-sig it cannot be resolved structurally, which is the same conclusion I·2 already reaches — single-sig funding wants a genuinely air-gapped signer.

A macaroon that can do nothing else

Do not hand this tool admin.macaroon. LND's bakemacaroon accepts a special uri entity whose action is a literal gRPC method path, so the credential can be restricted to precisely the calls the tool makes — and to nothing else. Broad entities are too coarse to be safe here: offchain:write would also grant SendPayment, and onchain:write would grant SendCoins.

Fifteen methods. The credential cannot send coins, cannot send payments, cannot close a channel, and cannot sign a message. Worth checking the list against the sequence yourself rather than trusting it — if a method is missing the tool fails loudly at setup, which is the right direction to fail in.

The watch-only wallet

One private-key-less descriptor wallet in Core, holding the cold wallet's descriptors. This is what gives us coin selection, change derivation, exact fee rates and PSBT construction with the bip32 derivations signers need — for no bespoke cryptography.

Two setup trapsThe timestamp is the wallet's birthday, not now. Pass "now" and Core will report a zero balance because it never scanned the blocks your coins arrived in. And the rescan it does perform takes minutes to hours — so import during setup, never during a batch. Second: sortedmulti and multi produce entirely different addresses from identical keys. Getting that wrong yields a wallet that imports cleanly, shows a zero balance, and tells you nothing about why.

Which is why setup ends in a round-trip check rather than a success message: the tool derives the first few receive and change addresses from the imported descriptors and asks the operator to confirm they match what their own wallet software displays. That single comparison catches wrong derivation paths, multi-versus-sortedmulti errors, transposed keys, and truncated xpubs — the whole family of descriptor mistakes, at the only moment when catching them is free.

Validating peers without asking anyone

All of it can be done through LND, and most of it without touching the network at all. Three tiers of certainty:

There is no gossip field for "minimum channel size" — it is enforced conversationally, in accept_channel. So the only authoritative check is to ask, and the design already has a zero-cost way to ask: a shim probe that is cancelled with shim_cancel. Which means peer limits get discovered during rehearsal instead of at step 2 with the clock running, and third-party Lightning explorers stay out of the picture entirely.

Hostingand configuration

One binary, two sockets, no internet

A single static binary plus a SQLite file. It serves the UI, talks to LND over gRPC and to Core over JSON-RPC, and has no other dependencies and no cloud component. Three deployment shapes, in descending order of how much I would recommend them:

On the node — preferred

Runs on the LND box, bound to loopback. Both credentials stay on the machine that already holds them; reach the UI through an SSH tunnel. Nothing new is exposed and no secret is copied anywhere.

Coordinator over a tailnet

Runs on the laptop the signers plug into, reaching LND and Core over Tailscale. More convenient for SD-card and QR work, at the cost of copying tls.cert and the baked macaroon onto a second machine.

Anything public

No. There is no authentication model that makes a channel-opening UI worth exposing, and the tool refuses to bind a non-loopback address unless a config key explicitly names the interface.

Two rules the server keeps

A localhost bind is not an authentication boundary. Any process on the machine can reach it, and any web page the operator visits can attempt DNS rebinding against it. So: a token printed to the terminal at startup and required on every request, plus strict Origin and Host validation, and no CORS at all.

No sockets of its own. The rule is about who opens connections, not about keeping the batch hermetic — LND is a network node and will talk to peers, which is the point. What the app must never do is contact a third party: fee estimates come from Core's estimatesmartfee and peer facts come from LND's local graph, never from a block explorer, a fee API, or a Lightning explorer. Amounts, peer sets and timing are exactly the things those services log. Anything the app needs from the network, it asks LND for.

Setup the tool checks itself

A written guide is necessary and will rot. So the guide is short and the tool carries the checks: winthistle doctor tests every prerequisite in turn — LND reachable, macaroon sufficient for each method it will call, Core present or absent and pruned or not, descriptors imported and rescanned, peers resolvable in the graph — and for each failure prints the exact command that fixes it rather than prose describing it.

The macaroon is the case where that matters most, because the required permission list is a property of the code. So the tool generates the baking command from its own method registry: winthistle print-macaroon-command emits the lncli bakemacaroon line for exactly the methods this build calls. The list in this document is illustrative; the one the tool prints is authoritative, and it cannot drift from what the code does.

What stays in prose is the part no program can do for you: exporting descriptors from your own wallet, registering the multisig on each device, and choosing peers and channel sizes. That is a page, not a manual.

The journal is the one piece of state worth backing up — it holds each run's pending channel IDs, funding outpoints and the finalized raw transaction, which is what makes a crashed run recoverable rather than mysterious. It contains no key material.

Recoverywhen it goes wrong

One question decides everything

Under pressure the only thing that matters is whether the transaction reached the network. The app answers that from its own journal plus a mempool and chain lookup, and then offers exactly one path.

Has the funding transaction been broadcast?
No — nothing is at risk, and nothing has cost anything. Cancel every shim with shim_cancel, abandon any channel that reached pending, release the Core UTXO locks, and either re-arm or walk away. No on-chain footprint, no fees. Because of I·1 this covers every failure before the gate, which is every failure the batch is actually likely to have.
Yes — then all n channels reached chan_pending before it went out, because that is the only condition under which the app will publish. Every channel therefore holds its peer's commitment signature and every outpoint is watched by the ChainArbitrator. Three ways this ends, all of them solvent: the transaction confirms and the channels open; a peer vanishes and a force-close recovers the funds; or our own node is lost and the exported backup plus the peer's data-loss protection recovers them.
The branch that used to be hereAn earlier revision of this document described a third outcome: published, but with a channel that never completed negotiation, whose output is a 2-of-2 with a counterparty who never signed — coins gone. This design has no path that reaches it. Two things close it. I·1 means the transaction is not published until every channel is already recoverable, and I·2 means no other party ever holds a transaction it could publish for us. Remove either one and the branch comes back, which is why they are invariants and not preferences.
Residualhonest limits

What "no lost funds" does and does not cover

The claim this design earns is specific: no channel in a batch is ever left with an unspendable funding output. That entire class of loss is closed by construction, not by care. It is worth being equally precise about what remains, because a safety argument that overstates itself is worse than none.

Openverify first

Claims the cold probe has to settle

Each of these is load-bearing, and all but the last two are answered by a single cold probe. None should be taken on faith from documentation, including this document — the items marked as settled were read out of LND's source, which is better evidence than prose but still not a passing test.

  • Does shim_cancel still succeed after a successful psbt_verify? The whole re-arm story depends on it.
  • settled in source Does psbt_finalize with no_publish emit chan_pending without broadcasting? Yes — NoFundingTxBit skips only the broadcast block in handleFundingSigned, between CompleteReservation and the update. Confirm it empirically anyway; the gate depends on it.
  • Exactly when does each peer's ten-minute clock start — at OpenChannel, or at the peer's accept_channel? Determines what the countdown should actually display.
  • What does RequiredReserve return for private channels, given the field is named additional_public_channels?
  • past broadcast Will UpdateChannelPolicy accept a channel point that is pending but not yet active, or must Phase 2 poll? Assume it must, and the question stops mattering.
  • Does Core's finalizepsbt handle every signer's output for the specific multisig descriptor in use, or is a fallback finalizer needed?
  • past broadcast Does the settlement pass behave on a real confirmation — depth tracking, policy application, CPFP offer? Only the first small live batch answers this.
