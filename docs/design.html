Channel Opener

A local, guided interface for opening a batch of Lightning channels in one transaction, funded straight from cold storage — including multisig cold storage — without the tmux choreography.

Premisewhat this replaces

The work is coordination, not cryptography

The manual process works. What makes it arduous is that a human is holding the state machine in their head: which pane is which peer, which prompt wants base64 and which wants raw hex, which pane has --no_publish, how much reserve LND will demand once the new channels exist, and how many of the ten minutes are left. Every one of those is mechanical, and every one of them is a place to lose a channel — or, in the worst case, coins.

So this tool owns the state machine and the clock, and hands the human back exactly two jobs: approve the transaction and sign it. Nothing else should require a decision under time pressure.

ScopeOne LND node, one funding transaction, n channels, funded by an external single-sig or m-of-n wallet whose keys never touch this machine.
Invariantsload-bearing

Four rules that shape everything else

These come from LND's own protocol constraints, not from preference, and each is enforced in code as a gate rather than documented as advice. The first one is the reason this tool can claim that no channel in a batch is ever left unrecoverable.

I·1

Publish only once every channel is already recoverable.

LND's "DO NOT PUBLISH" warning is about ordering, not authorship. The condition that actually matters is that the transaction must not reach the network before every channel has received its peer's funding_signed — the counterparty signature on our initial commitment transaction, which is precisely what lets a force-close recover the funds.

In funding/manager.go, chan_pending is emitted strictly after CompleteReservation(nil, commitSig) has stored that signature and after WatchNewChannel has handed the outpoint to the ChainArbitrator. So n chan_pending events is exactly the safe condition — and we gate on it: no_publish is set on every channel, not all but the last. Once all n report pending, we publish. There is no ordering in which the transaction can reach the network while any channel is still unrecoverable, because we hold the only copy of it until the gate opens.

I·2

The app holds the last signature.

I·1 is only true if nothing else can broadcast. A fully-signed transaction is a bearer instrument: any party holding one can publish it, buggily or maliciously, before the gate opens. So signers return partial signatures, and combining and finalizing happen in-app — no external device ever possesses a broadcastable transaction. For m-of-n this falls out for free. For single-sig it cannot, since the lone signer necessarily produces a complete transaction; there, a genuinely air-gapped signer with no network path is a requirement rather than a preference.

I·3

The TXID must not move after verification.

LND commits to the funding outpoint at psbt_verify: "no inputs or outputs can change, only signatures can be added. If the TXID changes between this call and the publish step then the channel will never be created and the funds will be in limbo." A signer that re-selects coins or re-derives change silently breaks the batch, so the app hashes the verified transaction and refuses any returned PSBT whose unsigned TXID differs, naming the device that did it.

That check is not a duplicate of LND's, because LND's is narrower than the sentence above sounds. PsbtIntent.FinalizeRawTX compares the outputs and the inputs' previous outpoints and stops — "the fields in the PSBT part are allowed to change" — and sequence numbers, version and locktime live in the wire transaction rather than in the PSBT part. CompileFundingTx then takes the channel point from i.FinalTX.TxHash(), the transaction it was just handed. So a returned transaction with different sequence numbers has a different TXID and LND would adopt it — replaceability included, which is I·4's whole hazard. Nor does LND check the signatures: verifyInputsSigned only asserts that each input has something attached. Both gaps are closed before LND is asked.

This is also why LND's verifyAllInputsSegWit rejects legacy inputs outright — "risk of malleability". A malleable input is a TXID that can move after we have committed to it, which is the same failure wearing a different hat.

I·4

No RBF on the funding transaction, ever. CPFP or wait.

Replacing the funding transaction changes the outpoints and destroys every channel in the batch. No code path in this build replaces one, and the batch verifier refuses any funding input that signals replaceability.

The change output is a mitigation, not part of the invariant — but it is still required. This paragraph used to read "therefore always include a change output we control", which conflated what I·4 forbids with what it costs. A stuck batch can only be accelerated by spending its change, so a change output is the only lever, and the verifier refuses a batch without one or with one too small to matter. What that gate protects is not the coins — nothing is at risk in an unconfirmed transaction only we could have signed — but the signing ceremony, and the escape from a batch that has no way out at all. See A batch that never confirms.

replaceable: false is a statement of intent, not a defence — and this is a correction. The paragraph above used to end "disable replaceability in the UI entirely", which implied the flag protected something. Measured against Bitcoin Core v29, the version this build develops against: mempoolfullrbf does not exist even as a hidden debug option, and getmempoolinfo reports "fullrbf": true with no way to turn it off. Full-RBF is unconditional, so a higher-fee conflict relays regardless of what our sequence numbers signal. The flag is still set, and should be — but what actually enforces I·4 is that only we can sign our inputs, and nothing here builds a replacement.

Building that child is winthistle bump, and it is not a small command. The change output belongs to cold storage, so the child comes back unsigned and accelerating a batch costs a second cold-wallet session — its own transport, its own verification, its own journal rows. There is no shortcut that does not amount to a hot key able to spend the batch's change, which is I·2 again from the other end.

The child itself is always replaceable, and the distinction is the whole of this invariant's scope. The funding transaction can never be replaced: n peers hold commitment signatures against its outpoints, replaceability is off at construction, and the batch verifier refuses any input that signals it. A child is the opposite case in every respect — nobody has committed to anything about it, it spends the batch's change and pays cold storage back, and only cold storage can sign a replacement of it. So it is built BIP-125 replaceable and the child verifier requires that, which is what makes a second lift an ordinary replacement rather than a grandchild paying for a longer chain. Two verifiers is what lets both rules be stated at once; one verifier with a flag on it would be a switch on the invariant.

Two consequences worth knowing before asking for a second lift. A replacement has to beat the standing child's absolute fee, not merely its rate — BIP-125 rule 3, plus rule 4's charge for its own bandwidth — and Core's refusal for that says only insufficient fee, naming neither figure, so the app checks it before a device is asked and says what target would clear it. And the sequence number is pinned to exactly 0xfffffffd rather than to anything replaceable: the child is a version 2 transaction, so a sequence with bit 31 clear stops being an RBF signal and becomes a BIP-68 relative timelock, and a child that cannot be mined beside its parent cannot enter a mempool at all.

The child also has a ceiling nothing else in this design meets, and it is worth stating because it is discovered at the worst possible moment otherwise. A child concentrates the whole package's lift into about 150 virtual bytes, so its own fee rate is roughly parentVsize / childVsize times the package target — a multiplier near fifty on a three-channel batch. WalletKit.PublishTransaction hands the transaction to btcwallet, which calls SendRawTransaction(tx, false); rpcclient turns that false into maxfeerate: 0.1 BTC/kvB, and no WalletKit parameter reaches it. So above 10,000 sat/vB of the child's own rate — about a 210 sat/vB package target on a 7,000 vB parent, less on a larger batch — the node declines to relay a perfectly valid transaction. The app refuses that lift before the signing round and says both ways out: ask for a smaller lift, or hand the signed child to Core directly with sendrawtransaction <hex> 0, which is the same bytes by a route that takes an argument. Measured against Core 29: refused at the default with max-fee-exceeded, accepted with maxfeerate 0.

Cost of I·1Setting no_publish on every channel also sets NoFundingTxBit, and that bit gates rebroadcastFundingTx — so LND will not re-broadcast the funding transaction on restart. We inherit that duty. Publishing through WalletKit.PublishTransaction rather than bitcoind hands the transaction to LND's wallet-level rebroadcaster, which "will continually attempt to re-broadcast the transaction on start up, until it enters the chain", restoring the property by another route. The raw transaction is also kept in the run journal so we can re-broadcast independently.
Sequencethe funding flow

What the app actually drives

The interactive lncli prompts exist only because the CLI is interactive. Underneath is a plain gRPC state machine, fully scriptable, and the client generates the identifiers — so the app owns every handle from the first call.

Chaining is an ergonomic crutch for the CLI — we build the transaction ourselves. And skip_finalize skips the very step that produces the chan_pending gate in step 8, which is the one thing this design will not give up.
Constraintthe ten minutes

Budgeting the window

An LND peer forgets a pending channel after roughly ten minutes, and LND's own docs concede there's no reliable way to know the deadline for a non-LND peer. With n parallel streams there are n clocks starting at slightly different moments, so the real budget is the earliest one. The app shows a single countdown: the minimum remaining across all streams.

Machine work inside that window is trivial — well under a minute for a realistic batch. Effectively the entire budget belongs to humans handling hardware. That reframing is what the phase model below is built on.

The 5:00 line is a hard gate, not a warning: if rehearsal showed a signing round-trip slower than five minutes, the app will not arm the batch. Note what running out of time now costs, though. Because nothing is published until the step 8 gate, a lapsed window strands no channels and spends no fees — it costs one more signing round. The clock is an inconvenience, not a hazard.

Modelthree phases

Move every slow thing outside the clock

The reason the manual process is stressful is that it begins the countdown before anyone knows whether the signing setup works. Splitting the run into a rehearsal, an armed window, and a settlement pass means the clock only ever covers work whose duration has already been measured.

0

Rehearsal

no clock running

No funding streams are open, so nothing can time out. Everything here is repeatable and free.

  1. Peer pre-flight. Connect to each peer, validate the key on the curve, and read what LND's own gossip graph knows — alias, addresses, and the capacities of the channels that peer already has. That last is the only evidence available about what it will accept, and it is evidence rather than a limit. Do not promise "usable after k confirmations" here: minimum_depth cannot be read. The peer states it in accept_channel; LND stores it as OpenChannel.NumConfsRequired and exposes it over no RPC — min_accept_depth appears in lnrpc only on ChannelAcceptResponse, which is the responder's side of somebody else's channel. What can be shown up front is a prediction from LND's own default policy (3 to 6, scaled by capacity), labelled as one. The real figure is learned in Phase 2, after the fact — see the confirmation watch.
  2. Reserve arithmetic. Ask LND, don't guess: WalletKit.RequiredReserve, compared against the balance LND itself will judge — the node's own unspent witness outputs in the default account, unlocked, at zero confirmations, which is what CheckReservedValue sums. Two figures, not one: additional_public_channels = 1 is what psbt_verify will demand, because none of the batch is in the channel database yet, and = n is what the node needs once all of them are pending. Block on the first, warn on the second, and add a top-up output to a fresh p2tr node address for any shortfall — CheckReservedValue credits outputs that pay into the wallet, so a top-up inside the batch counts at step 5 with no extra transaction and no wait. Private members do not count at all: enforceNewReservedValue returns early for an unannounced channel.
  3. Lock the coin set and the fee rate. Segwit inputs only, confirmed inputs only, with a change output sized so a CPFP child could pay for itself.
  4. Choose the forwarding policy, per peer. It belongs here and it belongs in the plan document, beside the amounts, because it is the same decision: a channel's capacity and what it will charge to route are chosen together or the second one is not chosen at all. Nobody is asked again — Phase 2 applies it in a loop with no human in it — and a channel with no policy is not neutral, it is LND's defaults of 1000 msat and 1 ppm, which on a large channel is close to free routing for whoever notices first. A policy LND would refuse is refused here too, where it costs nothing: UpdateChannelPolicy reports an invalid CLTV delta inside a successful response, and by Phase 2 the transaction is public.
  5. Dress rehearsal. Build a decoy PSBT — same inputs, same fee, outputs paying back to the cold wallet — and push it through every signer for real. Confirm each device produces a valid witness, combine and finalize it, run testmempoolaccept, then throw it away.
  6. Record the measurement. The rehearsal's wall-clock signing time becomes the gate on Phase 1.

This phase catches the two failures that cost the most last time: a signer that produces malformed witnesses, and a reserve shortfall discovered mid-window.

1

Armed window

countdown live

Steps 1–8 of the sequence above, with the countdown visible throughout. The transaction shape is already decided; only the funding addresses are new.

  • Re-arm is one action. If the window lapses, cancel every shim with FundingStateStep{shim_cancel{pending_chan_id}}, reopen the streams for fresh addresses, and re-issue the same transaction with the outputs swapped. Nothing has been broadcast, so nothing is lost — the cost is one more signing round.
  • Sequential fallback. If signers are too slow to batch at all, the app offers one channel per transaction. More fees, no atomicity, but it completes. Naming this as a supported mode beats discovering it at 9:30 on the clock.
  • Nothing else is clickable. During the window the UI shows the countdown, the signing tracker, and abort. No settings, no editable fields.
2

Settlement

until confirmed + active

The transaction is public and the channels are pending. Two things still need watching.

  • Close the fee-policy race. New channels sit at LND's defaults — 1000 msat base, 1 ppm — from the moment they go active. The app takes the channel point from each chan_pending, polls until the channel is active, and applies the intended policy via UpdateChannelPolicy immediately. Policy is chosen per peer back in Phase 0, so this needs no human at all.
  • Confirmation watch. Track depth — from Core, since LND reports no confirmation count for a pending channel either — and offer the CPFP child from the change output if the batch stalls — winthistle bump, which is a second cold-wallet session rather than a button. Never offer a replacement. The depth to compare against cannot be asked for, so it is observed: the number of confirmations a channel has when it first appears in ListChannels is that peer's minimum_depth, from above. It is authoritative, it arrives far too late to plan with, and it is exactly the right thing to record for the next batch.
Commissioningproving it once

The state machine, tested on mainnet, at zero cost

Phase 0 opens no funding streams — that is exactly what makes it untimed, and exactly why it cannot vouch for LND's funding flow. Signers, descriptors and fee arithmetic are the things rehearsal proves. Everything in the sequence from step 2 onward is untested by it.

Rather than stand up a signet node for that, we lean on the property that already governs this design: nothing is at risk until broadcast. Every step short of publishing can therefore run against mainnet, against real peers, with real coins that never move.

I·1 makes this sharper than a test mode. Because no_publish is set on every channel in the production flow, the probe is not a separate code path — it is the real run with the final action withheld. There is no rehearsal-only branch that could behave differently on the day, and step 9 is the only line of code the probe does not execute.

It is winthistle run --stop-before-publish, and the claim above survived being built: composing it forced exactly one branch, an if between arm.Finalize and arm.Publish. Everything above that line runs unconditionally, the flag is read nowhere else, and the type system carries the rest of the argument — Publish takes an *arm.Armed whose raw transaction lives in an unexported field that only Finalize fills. What differs after the branch is not a code path but a fact: nothing was published, so the run terminates through the abort path, which is the other half of what the probe proves.

C

Cold probe

run once per setup

Steps 1 through 8 exactly as production runs them. Step 9 is simply not taken.

  1. Open the streams, build and verify a genuine PSBT, sign it with the real devices, combine and finalize in-app, and confirm testmempoolaccept passes.
  2. Finalize all n channels and watch every chan_pending arrive. Confirm the gate at step 8 closes as expected — this is the assertion the whole safety argument rests on.
  3. Export the channel backups, verifying that step works on pending channels.
  4. Stop. Then clear up, which the run does itself rather than suggesting: AbandonChannel for each pending channel — expect pending_funding_shim_only to be refused and the blunt flag to be asked for, which is the normal route here and not a warning sign — shim_cancel for any stream that never finalized, and release the Core UTXO locks.
  5. Separately, deliberately let one stream lapse without finalizing, to observe the peer timeout for real rather than trusting the ten-minute figure.

Cost: nothing on-chain. The only externality is a briefly held reservation on each peer, which their own timeout clears.

That covers most of the questions the design has to settle. The two it cannot reach both sit past the broadcast line — whether UpdateChannelPolicy accepts a pending-but-inactive channel point, and the settlement path as a whole — and both have since been answered on regtest instead, where a batch really can be published and then watched to confirmation. That is a weaker result than a probe against real peers and it is the right kind of weaker: the code path is the same one, and only the counterparties are not. The remaining exposure is settled by making the first live run a deliberately small one — two channels at the smallest size the chosen peers accept — treated as commissioning rather than as a real allocation.

Consequence for the build orderThe abort and recovery paths must therefore be working before the first mainnet probe, since the probe's normal termination is the abort path. That inverts the usual order: shim_cancel, AbandonChannel and the UTXO-lock release ship first, and the happy path is built on top of them.
Which abandon flagTry pending_funding_shim_only first: it refuses unless the channel is both shim-funded and pending, so it structurally cannot touch a confirmed channel. On regtest it refuses every channel this app opens. rpcserver.go infers "shim funded" from ThawHeight > 0 — there is a standing TODO about storing the funding type properly — and a plain PSBT open carries no thaw height, so the safe flag rejects with "channel … is not externally funded or not pending" on the ordinary path. The fallback to i_know_what_i_am_doing is therefore the standard route rather than an edge case, which moves the burden of safety off LND's flag and onto ours: before escalating, the app re-establishes the missing half of the check itself by asking PendingChannels. If the channel is not pending it refuses outright and offers no confirmation, because there is nothing a human could usefully authorise there.
Architecturecomponents

Where the pieces live

The trust boundary is the design's most important line. The app holds an LND admin macaroon and Core RPC credentials; it never holds key material, and it is never exposed to the internet.

Note what carries the PSBT between the two machines: the browser. The UI is viewed on the desktop through the tunnel, so a download hands the PSBT to Sparrow and an upload hands it back — no file sync, no shared mount, no extra daemon. The topology most people already have turns out to be the transport.

Two engines, one safety model

With Core, the app builds the transaction itself and owns coin selection, change and fee rate. Without it, Sparrow builds and the app verifies. The LND sequence and all four invariants are identical either way — see below.

Resumable by default

A closed tab must never orphan a funding stream. SQLite records each pending channel ID against its funding address and output index, per-signer signature state, and the finalized raw transaction — written before the publishing call, so the artifacts survive a crash mid-publish.

Transport, not typing

Base64 in and out, file download and upload, and animated QR — BBQr and ur:crypto-psbt — with webcam capture on the return leg. This is the one place a browser UI is genuinely better than a terminal, and it is where multisig ergonomics are won.

Commissioning without a testnet

No signet or regtest harness. Instead, the state machine is proven on mainnet with real peers and zero on-chain cost, by exercising every step up to but excluding broadcast. See Commissioning below — that mode is a first-class part of v1, not a debug affordance.

Two engines

Requiring a fully-synced, unpruned Bitcoin Core is the heaviest thing in the prerequisites, and for a lot of otherwise well-run nodes it is a blocker — Umbrel and friends often prune by default, and a descriptor import needs blocks a pruned node has thrown away. So Core is optional, and the difference between the two modes is convenience, not safety.

In assisted mode the app emits a batch plan — every funding address with its exact amount, the reserve top-up, a target fee rate and the input constraints — and then verifies what comes back, output by output: each funding script present exactly once at exactly the right amount, no outputs to scripts the plan does not name, fee rate within tolerance, every input segwit and confirmed. That check is strictly mechanical and it is the same check LND's own psbt_verify will repeat at step 5.

On losing testmempoolacceptLess of a loss than it sounds. Executing every input's script locally against the witness data in the PSBT answers the question we actually care about — will each input validate — more directly than a mempool acceptance test does, and needs no chain data. What testmempoolaccept adds on top is node policy: min relay fee, standardness, ancestor limits. Worth having, and worth a warning when it is unavailable, but not load-bearing.
Where assisted mode is genuinely weakerI·2 says no external party ever holds a broadcastable transaction. In assisted mode Sparrow builds and signs, so the operator must stop short of Sparrow's own broadcast button. For m-of-n that resolves cleanly: let Sparrow apply m−1 signatures and have the app collect the last partial, and Sparrow never holds a complete transaction. For single-sig it cannot be resolved structurally, which is the same conclusion I·2 already reaches — single-sig funding wants a genuinely air-gapped signer.

Do not hand this tool admin.macaroon. LND's bakemacaroon accepts a special uri entity whose action is a literal gRPC method path, so the credential can be restricted to precisely the calls the tool makes — and to nothing else. Broad entities are too coarse to be safe here: offchain:write would also grant SendPayment, and onchain:write would grant SendCoins.

The watch-only wallet

One private-key-less descriptor wallet in Core, holding the cold wallet's descriptors. This is what gives us coin selection, change derivation, exact fee rates and PSBT construction with the bip32 derivations signers need — for no bespoke cryptography.

   "active":true, "internal":false, "range":[0,999], "timestamp":1700000000},
  {"desc":"wsh(sortedmulti(2,[aabbccdd/48h/0h/0h/2h]xpubA/1/*,…))#cksum",
   "active":true, "internal":true,  "range":[0,999], "timestamp":1700000000}
]'
Four setup trapsThe timestamp is the wallet's birthday, not now. Pass "now" and Core will report a zero balance because it never scanned the blocks your coins arrived in. And the rescan it does perform takes minutes to hours — so import during setup, never during a batch. Second: sortedmulti and multi produce different addresses from identical keys — but not at every index. sortedmulti sorts the derived pubkeys, so the two agree wherever the keys already happen to be in ascending order: about half the indices for two keys. So the wrong wallet is not empty, it is plausible — measured against the harness's own 2-of-2, a multi()-where-you-wanted-sortedmulti() wallet found most of the cold wallet's balance, and index 0 agreed on both fixtures. A partial balance is a far better disguise than zero, and an operator who compared one address would have passed a wrong descriptor. Third: a descriptor with a <0;1> multipath step is silently halved. getdescriptorinfo returns the first branch alone, under a different checksum from the one it was given, so pasting one line into both fields imports the receive branch where the change branch belongs — and the wallet then derives change to the addresses the batch is also funded from. Split it into two descriptors. Fourth: Core cannot forget a descriptor. A wallet holds one active receive branch and one active change branch; importing a corrected pair deactivates the wrong pair rather than removing it, and a deactivated descriptor's coins are still in listunspent. There is no RPC that removes one. So a descriptor that failed the address check is corrected by starting a new wallet, not by importing over the top.

Which is why setup ends in a round-trip check rather than a success message: the tool derives the first several receive and change addresses from the imported descriptors and asks the operator to confirm they match what their own wallet software displays. Several rather than one, for the reason above — five leaves roughly a three per cent chance of a whole sample agreeing for a 2-of-2, and less for larger quorums. That single comparison catches wrong derivation paths, multi-versus-sortedmulti errors, transposed keys, and truncated xpubs — the whole family of descriptor mistakes, at the only moment when catching them is free.

It is also the only step here whose evidence is a person, so the answer is written down: winthistle setup records it in the run journal against the exact descriptors that were compared, and winthistle doctor reads it back. Keying it to the descriptors is what stops it ageing into a claim — an answer given before a re-import describes a pair the wallet no longer derives from, and the pre-flight says so rather than believing it. A wallet whose descriptors were explicitly rejected is refused outright — by the pre-flight and by the run itself, before it asks LND anything, since a refusal that early has cost nothing; one nobody has ever compared is a warning, because a wallet imported by hand is a working wallet that has not been checked. There is no flag that overrides the refusal, for the same reason there is no flag that answers the question: the way past it is to compare the addresses again, or to start a new wallet.

Validating peers without asking anyone

All of it can be done through LND, and most of it without touching the network at all. Three tiers of certainty:

CheckSourceCost

A probe the peer accepts holds one of its pending-channel slots for about eleven minutes — see below

There is no gossip field for "minimum channel size" — it is enforced conversationally, in accept_channel. So the only authoritative check is to ask, and third-party Lightning explorers stay out of the picture entirely. Asking is a shim probe that is then cancelled with shim_cancel.

The probe is not freeReading handleFundingOpen in order: the peer counts its live reservations for us plus its pending channels with no thaw height, and refuses with ErrMaxPendingChannels if that count already reaches --maxpendingchannels — LND's default for which is 1. Only after every limit check does it call InitChannelReservation and send accept_channel. So the cost splits in two, in opposite directions. A probe the peer refuses costs nothing at all: no reservation is created, so probing downwards to find a peer's minimum is free however many times you do it. A probe the peer accepts costs one of that peer's pending-channel slots, and shim_cancel does not give it back — CancelFundingIntent deletes an entry in our own wallet's map and sends the peer nothing. Only the peer's own zombie sweeper releases it, after ten minutes plus up to a minute of sweeper granularity.

Which changes where the probe belongs. A Phase 0 that probes all n peers and then arms collides with its own probes: against a peer running the default, step 2 is refused with "Number of pending channels exceed maximum" — on the clock, with the cold wallet out, for a reason we created ourselves a minute earlier. Three consequences:

  • Do not probe as part of arming. A successful probe is step 2 with the answer thrown away: same RPC, same no_publish shim, same reservation, same ten minutes. If the batch is ready to arm, arm it — the open asks the same question and keeps what comes back.
  • Probe as a separate, earlier act, when a peer's minimum is genuinely unknown and the graph's capacity evidence is not good enough. Then wait out the hold before arming; the app gates on it rather than trusting the operator to remember.
  • The probe therefore starts a clock — the one property Phase 0 was defined by not having. Worth saying out loud in the UI rather than discovering.

One thing to know about reading the refusal: the peer's own words do survive, because failFundingFlow forwards the real text for a reservation error, a funding error or a channel-acceptor error. They arrive under a claim that is not true, though. handleErrorMsg wraps every peer error in chanfunding.ErrRemoteCanceled when the reservation is a PSBT one, so a peer that refused in thirty milliseconds because the channel was too small arrives saying it "possibly timed out". Strip the wrapper and report what the peer actually said, alongside how long it actually took.

Hostingand configuration

One binary, two sockets, no internet

A single static binary plus a SQLite file. It serves the UI, talks to LND over gRPC and to Core over JSON-RPC, and has no other dependencies and no cloud component. Three deployment shapes, in descending order of how much I would recommend them:

On the node — preferred

Runs on the LND box, bound to loopback. Both credentials stay on the machine that already holds them; reach the UI through an SSH tunnel. Nothing new is exposed and no secret is copied anywhere.

Coordinator over a tailnet

Runs on the laptop the signers plug into, reaching LND and Core over Tailscale. More convenient for SD-card and QR work, at the cost of copying tls.cert and the baked macaroon onto a second machine.

Anything public

No. There is no authentication model that makes a channel-opening UI worth exposing, and the tool refuses to bind a non-loopback address unless a config key explicitly names the interface.

Two rules the server keeps

A localhost bind is not an authentication boundary. Any process on the machine can reach it, and any web page the operator visits can attempt DNS rebinding against it. So: a token printed to the terminal at startup and required on every request, plus strict Origin and Host validation, and no CORS at all.

No sockets of its own. The rule is about who opens connections, not about keeping the batch hermetic — LND is a network node and will talk to peers, which is the point. What the app must never do is contact a third party: fee estimates come from Core's estimatesmartfee and peer facts come from LND's local graph, never from a block explorer, a fee API, or a Lightning explorer. Amounts, peer sets and timing are exactly the things those services log. Anything the app needs from the network, it asks LND for.

Configuration

Two files, deliberately separate. winthistle.toml holds connection details and never contains a secret, only paths to them. The batch file is where the money is: peers, amounts, and what each channel will charge to route. The batch plan is the reviewable artifact built from the two of them plus what only LND and Core can supply — the funding addresses, the coin set, the fee rate and the reserve top-up. It is written and checked during Phase 0, and it is what the armed window executes.

There is no allow_rbf key, and writing one is refused rather than ignored. An earlier revision of this block had it, set to false, described as not operator-adjustable — but a key that appears in a config file and changes nothing is worse than no key at all, because an operator who sets it to true and watches the run proceed will reasonably conclude it was honoured. I·4 is enforced at construction and nothing reads a preference about it, so the reader refuses the line and says why.

The fee floor has no default, and that is the point. estimatesmartfee is entitled to answer "insufficient data" — it does so on every regtest node, on a freshly synced one, and on any node that has been offline for a while — and it answers with a 200 and no rate rather than an error. The batch's rate is the largest of Core's estimate, the node's relay floor, and this figure; a node with no estimate and no configured floor is an error rather than a guess, because I·4 means a rate chosen badly cannot be corrected by replacing the transaction. winthistle doctor says so before the evening rather than during it.

Every unknown section and every unknown key is refused, naming the line. That is not pedantry: the file is read once, at the start of a run that may end with a cold wallet on the table, and a misspelled abort_after_signing_seconds that silently defaults has told the operator nothing.

Setup the tool checks itself

A written guide is necessary and will rot. So the guide is short and the tool carries the checks: winthistle doctor tests every prerequisite in turn — LND reachable, macaroon sufficient for each method it will call, Core present or absent and pruned or not, descriptors imported and rescanned, peers resolvable in the graph — and for each failure prints the exact command that fixes it rather than prose describing it.

The macaroon is the case where that matters most, because the required permission list is a property of the code. So the tool generates the baking command from its own method registry: winthistle print-macaroon-command emits the lncli bakemacaroon line for exactly the methods this build calls. The list in this document is illustrative; the one the tool prints is authoritative, and it cannot drift from what the code does. “Cannot” is doing work there: the client refuses at dial time to call a method the registry does not list, and a test type-checks the whole module and fails if the registry and the call sites disagree in either direction — a missing entry breaks the app, and a spare one hands the operator a permission for nothing.

The credential is checked by asking, not by calling. The obvious way to find out whether a macaroon authorises a method is to invoke it, and for most of this list that is a bad idea: the interceptor runs before the handler, so a refused method costs nothing, but an allowed one runs, and AbandonChannel and PublishTransaction are not things to try with junk arguments to see what happens. CheckMacaroonPermissions answers directly — it examines the macaroon in the request rather than the caller's, runs the same check the interceptor would, and reaches no handler.

That also checks the half nothing else could: the never-list. The registry promises the credential cannot send coins, close a channel, sign a message or widen itself, and that is a promise about the file in the operator's config rather than about this build's intentions. An operator who points the tool at admin.macaroon has broken every part of it while everything still works, so doctor asks LND whether the credential holds onchain:write and the rest, and fails if it does. One warning about the two refusals that look alike: a credential that does not authorise a method is reported as InvalidArgument, while the interceptor refusing the caller arrives as an untyped error — bakery.ErrPermissionDenied is a plain errgo error with no gRPC status attached, so it is codes.Unknown carrying the text "permission denied". Matching on the code alone confuses them; so does matching on the text alone.

What stays in prose is the part no program can do for you: exporting descriptors from your own wallet, registering the multisig on each device, and choosing peers and channel sizes. That is a page, not a manual.

The journal is the one piece of state worth backing up — it holds each run's pending channel IDs, funding outpoints and the finalized raw transaction, which is what makes a crashed run recoverable rather than mysterious. It contains no key material.

Recoverywhen it goes wrong

One question decides everything

Under pressure the only thing that matters is whether the transaction reached the network. The app answers that from its own journal plus a mempool and chain lookup, and then offers exactly one path.

Has the funding transaction been broadcast?
No — nothing is at risk, and nothing has cost anything. Cancel every shim with shim_cancel, abandon any channel that reached pending, release the Core UTXO locks, and either re-arm or walk away. No on-chain footprint, no fees. Because of I·1 this covers every failure before the gate, which is every failure the batch is actually likely to have.
Yes — then all n channels reached chan_pending before it went out, because that is the only condition under which the app will publish. Every channel therefore holds its peer's commitment signature and every outpoint is watched by the ChainArbitrator. Three ways this ends, all of them solvent: the transaction confirms and the channels open; a peer vanishes and a force-close recovers the funds; or our own node is lost and the exported backup plus the peer's data-loss protection recovers them.

Every state a run can be found in

The question above is answered from the run journal — SQLite, at ~/.winthistle/runs.db, written before each call it describes so that a crash leaves artifacts rather than mystery. There is no version table and no migration machinery: the schema is one CREATE TABLE IF NOT EXISTS block, and it grows by new tables rather than new columns. A run is in exactly one of these seven states, and the state is what decides whether winthistle recover will act at all.

The cost is that a publish refused by the node also lands here, and that is accepted: a broadcast that returned an error is not a broadcast that did not happen.

This design has no path that reaches it. Two things close it. I·1 means the transaction is not published until every channel is already recoverable, and I·2 means no other party ever holds a transaction it could publish for us. Remove either one and the branch comes back, which is why they are invariants and not preferences.

A batch that never confirms

This is the state the CPFP handle exists for, and it is worth naming exactly, because the earlier drafts of this document described it in language that made it sound like a loss. It is not one.

Nothing is at risk while the funding transaction is unconfirmed. The coins are ours, unspent, in a transaction only we could have signed. Every channel reached chan_pending, which makes it recoverable by force-close once the funding transaction confirms — before that there is no channel yet, only a promise. So the cost of a stuck batch is the ceremony: a cold-storage signing round, n peers' cooperation, the ten-minute windows, all to be done again.

But it cannot be abandoned, either. An unconfirmed funding transaction never becomes safe to abandon on its own: its inputs stay unspent, so it stays valid indefinitely, and eviction from mempools does not invalidate it. winthistle recover therefore refuses any run that reached the publish call — abandoning a pending channel whose funding transaction later confirms strands its funds with no force-close path, which is precisely LND's "DO NOT PUBLISH … OR THE FUNDS CAN BE LOST". A batch that never confirms leaves its coins frozen: not abortable, not safely spendable, waiting on the mempool.

That inverts what CPFP is for. It is not a speedup — it is the exit. Confirm the batch, then close the n channels normally if you no longer want them; that costs the funding fee plus n cooperative closes and is completely safe. This is the correct way to read the change-output gate: not insurance against slowness, but what keeps a batch from having no way out at all — which is also why the gate is proportionate, since the lever costs a few tens of thousands of satoshis and what it buys is unrecoverable by us.

The freeze is a thin tail: it needs the fee market to move further than the CPFP multiple allowed for, while WalletKit re-offers the transaction on every restart. And it is not a state CPFP can rescue after the fact — a child of an absent parent is an orphan, and winthistle bump refuses rather than pretending. The gate protects the case a child can address: a parent sitting in a mempool, confirming too slowly.

The one route out, which this build does not take If a batch is frozen and waiting is unacceptable, the only way to release the coins is to double-spend one of its inputs — and this build will not do it for you. Not because the operator cannot be trusted with it, but because building one would put a funding-transaction replacement in the codebase, and I·4 is a statement about what this program contains. The line is authorship, not knowledge: we can say what the only way out is, and still refuse to be the thing that does it.

The procedure, and the ordering that keeps it from losing funds:

  1. Do not abandon anything first. Every channel's state — including each peer's commitment signature — is what lets you force-close if the original confirms after all. Abandoning before the replacement is settled is the one move that turns a frozen batch into a lost one.
  2. Build and broadcast a transaction, with your own tools, spending at least one of the funding transaction's inputs back to cold storage. Full-RBF is unconditional in Core v29, so it will relay despite the original's replaceable: false.
  3. Wait for it to be deeply confirmed. Until then both transactions are live and you cannot know which wins. There is no signal that resolves this faster than confirmation depth.
  4. Only once the original is unmineable — every one of its inputs spent by a confirmed transaction — abandon the pending channels and release Core's coin locks.
  5. If the original confirms instead, you have channels rather than coins. Close them; if a peer has passed its ~2016-block horizon and forgotten, force-close, which works because of step 1.

The honest summary is that the safe version of this procedure is slow enough that it is rarely better than waiting — which is the argument for the change-output gate being mandatory rather than advisory, and for sizing it against a pessimistic CPFP target rather than a hopeful one.

Claimsverify first

Claims the cold probe has to settle

Each of these is load-bearing, and none should be taken on faith from documentation, including this document. Items marked settled in source were read out of LND's source — better evidence than prose, but still not a passing test. Items marked proven on regtest have one. All of them are now closed, which is a smaller claim than it sounds: closed means a test on a regtest node, and the one thing regtest cannot stand in for is the mainnet cold probe.

  • proven on regtest Does shim_cancel still succeed after a successful psbt_verify? Yes. The intent lives in LightningWallet.fundingIntents, and psbt_verify only attaches a verified packet to it, so cancelling still finds and clears it. Re-arming after a lapsed window is therefore free, as the phase model assumes.
  • proven on regtest Does psbt_finalize with no_publish emit chan_pending without broadcasting? Yes — NoFundingTxBit clears ChanType.HasFundingTx(), which is the condition gating the broadcast block in handleFundingSigned, between CompleteReservation and the update. Observed for n = 3, which is the form the gate actually relies on: three chan_pending receipts against one transaction, and the mempool checked after every psbt_finalize including the last — precisely where LND's own "all but the last" idiom would have broadcast. Then published once, confirmed, and all three channels opened.
  • settled in source Exactly when does each peer's ten-minute clock start — at OpenChannel, or at the peer's accept_channel? Neither, in the sense the question assumed: we have no clock at all. pruneZombieReservations skips PSBT reservations outright — "these reservations are always initiated by us and the remote peer is likely going to cancel them after some idle time anyway" — so the only clock is the peer's, and on the peer it is resCtx.lastUpdated, set by defer resCtx.updateTimestamp() at the end of handleFundingOpen: the same handler that sends accept_channel. The two candidates are one network round trip apart against a ten-minute budget, so the distinction is not measurable and does not matter. What does: the timeout is DefaultReservationTimeout = 10 minutes, checked by a sweeper on DefaultZombieSweeperInterval = 1 minute, and neither is adjustable in a release build. So start the countdown at our own OpenChannel call and treat 10:00 as an upper bound with up to a minute of slack past it — and remember none of it binds a peer that is not LND. Measured on regtest by TestWhoOwnsTheTenMinuteClock, which is skipped unless WINTHISTLE_SLOW is set because it takes eleven minutes: bob gave up 10m41s after our OpenChannel call — ten minutes plus the sweeper's granularity, as predicted. LND's wording for it is worth knowing because it is what the operator will see: "remote canceled funding, possibly timed out", wrapped around a peer error that says only "funding failed due to internal error". The "possibly" is ours, not the peer's.
  • settled in source What does RequiredReserve return for private channels, given the field is named additional_public_channels? It adds whatever you pass to CurrentNumAnchorChans() and has no idea whether the channels you are naming are public, so the caller must pass the count of announced members only. Private channels are invisible to the check twice over: CurrentNumAnchorChans skips them when counting, and enforceNewReservedValue returns before counting anything at all when the channel being opened is unannounced.
  • proven on regtest Will UpdateChannelPolicy accept a channel point that is pending but not yet active, or must Phase 2 poll? Neither, and the real answer is worse than both: the call does not fail. localchans.Manager.UpdatePolicy walks the graph's outgoing edges, finds no edge, falls through to FetchChannel, sees IsPending, and appends a FailedUpdate with reason UPDATE_FAILURE_PENDING and the text "not yet confirmed" — which rpcserver.go then returns inside a PolicyUpdateResponse with a nil error. So a caller that checked only the error would record a policy it had never applied and go on forwarding at 1000 msat and 1 ppm believing otherwise. Polling was the right instinct for a better reason than the question knew, and it is not sufficient on its own: every attempt has to be judged against failed_updates, and only an empty list is a success. Observed against a live node on an armed-but-unpublished channel. Retry PENDING, NOT_FOUND and INTERNAL_ERR; stop on INVALID_PARAMETER, which is the policy being wrong rather than the channel being early, and on UNKNOWN, which is LND declining to say and therefore gives nothing to wait for.
  • proven on regtest Does Core's finalizepsbt handle every signer's output for the specific multisig descriptor in use, or is a fallback finalizer needed? Answered by not needing Core. internal/combine merges the partials itself and btcd's MaybeFinalizeAll assembles the witness, which is then executed against each input's script locally before anything else sees the transaction — so Core's finalizer is not in the path in either engine. Corroborated rather than relied on: on the harness's wsh(sortedmulti(2,…)) the in-app result is byte-identical to Core's combinepsbt plus finalizepsbt. What btcd's finalizer needs is narrower than Core's, and both limits are checked up front with the counts in hand: a P2WSH witness script must be a bare m-of-n multisig, and it must carry exactly m signatures.
  • proven on regtest Does the settlement pass behave on a real confirmation — depth tracking, policy application, CPFP offer? Yes, on regtest, one block at a time: the channel opened at three confirmations, which matched the prediction from LND's default policy, and the intended policy landed and read back out of the announced graph. The CPFP child was built against a genuinely unconfirmed parent and lifted the package to the target — and doing that turned up a Core behaviour worth having: walletcreatefundedpsbt's fee_rate applies to the whole unconfirmed ancestor package, not to the child alone, and the fee it charges is ceil(rate × (parentVsize + childVsize)) − parentFee. That is term for term the expression the change output is sized with, so Core does the arithmetic and this design's job is to check it rather than to repeat it. Verified to the satoshi at 50, 200 and 600 sat/vB — and again at 20, 50 and 200 against a real stalled parent when winthistle bump was built on top of it, with the whole command then signing and broadcasting a child whose package rate Core's own ancestor accounting confirmed. The second lift was then proved the same way: Core builds a replacement spending an outpoint its own mempool already shows as spent (the input is named explicitly, so there is no coin selection to refuse it), the replaced child is evicted, and Core's ancestor accounting for the replacement excludes the transaction it replaced — so the package arithmetic is unchanged. Measured at 60 sat/vB against a standing 20 sat/vB child. That work turned up one refinement to the finding: "the unconfirmed ancestor package" means all of it, so when the parent has unconfirmed ancestors of its own the arithmetic has to use Core's ancestorsize and fees.ancestor rather than the transaction's own figures. A batch funded from confirmed coins makes the two identical, which is the ordinary case and exactly why it is easy to get wrong. None of that is mainnet. The first small live batch is still what turns a regtest result into evidence, which is what the commissioning section is for.
