# External review — pre-mainnet hardening

**Provenance: this document was written from `README.md` alone. The reviewer has
not read the source.** Every finding below is therefore a *hypothesis about the
code*, not an observation of it. Several may already be implemented, contradicted
by the design, or wrong about how the phases are structured.

**This is a record, not a work order.** The triage it asks for below was
carried out in August 2026, every finding was classified, and what came out of
it was acted on — most of it in the rewrite that followed. The triage document
itself has been deleted; git has it. What the review is still worth is what it
was written from: `README.md` alone. Where a reader with no source access
guessed wrong is a map of where the public documents mislead, and that is the
reason to keep it.

## Phase 0 — audit before acting

Work through every finding in this document and classify it:

- **DONE** — already implemented. Cite file and function.
- **PARTIAL** — exists but incomplete. Say what is missing.
- **WRONG** — the finding misreads the design. Say why.
- **VALID** — real gap, worth doing.
- **DEFER** — real but not now. Say what it is blocked on.

Two specific things to check against the code while triaging, because the whole
document is built on assumptions about them:

1. **Phase structure.** The findings assume: build → arm (finalize *n*, collect
   *n* receipts) → publish. If `run` is structured differently, say so — several
   items are misconceived if the phase boundaries are elsewhere.
2. **What `doctor` already covers.** Item 1 may be substantially built.

---

## Constraint that scopes every item

**The binary should stay small enough that someone about to push 10 BTC through
it can read it end to end.** Test every proposed change against "does this make
it harder to audit." That test is meant to kill features — it already killed
items 5 and 7 in their original form. The product here is the explanation as much
as the code. If an item as specified would add substantial surface, say so in
triage rather than building it.

---

## Implementation limits

Three areas are **specification-only**. Produce a written spec and tests; do not
write the implementation without an explicit go-ahead:

- **2b, signed-PSBT validation.** A plausible-looking but subtly wrong validator
  is worse than none, because it will be trusted.
- **5, pre-signed abort.** Creates a second bearer artefact. Design decision, not
  a coding task.
- **Anything touching the publish gate.** The *n*-of-*n* property is the one thing
  known to work. Do not refactor around it.

Everywhere else: small commits, one finding each, tests alongside.

# Findings

## 1. Peer preflight, before the cold session opens

**Claim.** The dominant mainnet failure is not fund loss, it is *partial arming*:
peer 2 drops between finalize 1 and finalize 2, leaving one armed channel, one
cold-signed transaction that can never be published, and a burnt signing session.
Recovery needs a fresh funding address for the failed channel, so a full re-sign
with every signer reassembled. Regtest with cooperative peers never shows this.

**Check first.** Does `doctor` already probe peers? Does `run` check anything
before opening the first shim?

**Proposed.** A preflight phase before any shim opens and before cold storage is
touched. Per peer: reachable/connected; `max_pending_channels` headroom; amount
within advertised min/max channel size; remote reserve and dust limits
satisfiable; no competing pending open. Locally: anchor reserve sufficient
*after* all *n* channels exist.

**Acceptance.** Fails closed, names the peer and the failing check, exits non-zero
having touched nothing. Same checks available read-only via `doctor --batch`.

**Priority: highest.** Converts an expensive failure into a cheap one, and shrinks
the window item 5 exists to cover.

## 2. Verification sheet and return-path validation

**Claim.** This is the largest gap and it is invisible from inside the tool.
Channel funding outputs are P2WSH 2-of-2 scripts between LND and the peer. **No
signing wallet can attribute them.** Sparrow, Coldcard, Jade, Passport all show
the operator payments to unrecognised addresses plus change. Nothing lets a human
confirm that amounts landed against the intended peers, or that nothing was
swapped. Airgapped verification that cannot verify is theatre.

**Check first.** Does `run` already print an output map before handing off the
PSBT? Does anything validate the signed PSBT before `FundingStateStep`?

**2a — verification sheet (implement).** Before emitting the unsigned PSBT, print:
output index, peer alias, peer pubkey prefix, amount, address — plus change
address, change amount, fee, feerate, input count. The operator reads it against
the signer's output list.

**2b — signed-PSBT validation (SPEC ONLY).** On return, before finalizing: every
output script matches the funding address LND issued for that channel; amounts
match the batch spec; change goes to a verified cold branch; no input added,
removed or swapped; fee within tolerance. Any mismatch aborts loudly. Same table
in both directions — human check outbound, machine check inbound.

Write the spec, write the test vectors including deliberately corrupted PSBTs,
then stop.

## 3. Adversarial harness

**Claim.** n=3 on regtest with cooperative peers is the easy case. Until the hard
cases are scripted the phase model is a hypothesis.

**Scenarios.** Peer disconnects between finalize 2 and 3; peer never responds to
`FundingStateStep`; LND restarts mid-batch after some receipts; funding timeout
expires with one receipt outstanding; `PublishTransaction` fails at the gate
(already-in-mempool, insufficient fee); duplicate receipt, or a receipt for a
channel not in the batch; bitcoind unreachable at publish time.

**Acceptance.** Each asserts an empty mempool wherever the batch must not have
gone out, **and** a run directory `recover` can act on. The second half matters as
much as the first.

## 4. Operator surface — TUI state table

**Claim.** The design calls for a local web interface. It is the largest unbuilt
thing in the repo and worth deciding deliberately rather than inheriting: an HTTP
server is more attack surface and more code to audit, in a tool selling
auditability. A TUI gets most of the value at a fraction of the cost.

**Check first.** How much batch state is already in one place? If it is spread
across the run loop, item 4's real work is consolidating it.

**Proposed.** `ratatui` + `crossterm`. One row per channel:

```
 WINTHISTLE  run 7f3a91                        phase: ARMING
 ───────────────────────────────────────────────────────────
  #  PEER          AMOUNT      STATE          RECEIPT
  1  bitrefill     5,000,000   ✓ pending      2m14s ago
  2  acinq         2,500,000   ✓ pending      1m02s ago
  3  kraken        2,500,000   … awaiting     —
 ───────────────────────────────────────────────────────────
  receipts 2/3     funding tx HELD      expires in 6:41
```

- `funding tx HELD` is the README's invariant asserted live — the field an
  operator looks at when nervous. Only the *n*-of-*n* gate flips it.
- Countdown amber under 2:00, red under 0:30.
- Phase colour as peripheral cue: grey building, amber arming, green published.
- Truncate the alias column, never wrap the table. Real aliases run long.
- The 2a sheet renders here during signing — the operator reads it off screen
  while driving the signer on the same machine.
- **Do not overload one key for abort.** Without item 5 it means "abandon and
  shred"; with item 5 it means "broadcast the abort." Different labels.

**The actual payoff** is the single struct holding whole-batch state — the same
one a web UI would serialise. Not wasted if the browser question returns.

## 5. Pre-signed abort — SPEC ONLY, flagged, off by default

**What it does not do.** It does not defend against a batch failing midway; not
publishing already handles that.

**What it does.** Defends against a compound failure: the signed transaction leaks
**and** the pending channels were since abandoned, so coins land in 2-of-2 outputs
with peers holding no record of them. Deleting a file is not provable — backups,
journalling filesystems, a stale run directory replayed later. The abort converts
"trust that we destroyed it" into "the inputs are gone."

**What it costs.** Two conflicting signed transactions in the world; a feerate
guessed weeks ahead for an unseeable mempool; a second bearer artefact with its
own handling rules; a griefing vector, since anyone holding the abort can nuke any
batch. It also breaks the cleanest sentence in the README — one artefact, one
gate, legible in a paragraph.

**Where it earns its place.** Geographically distributed signers, where the
alternative to pre-signing is a dead batch nobody can neutralise until everyone
reconvenes. Solo signer, keys in one city: shred and re-sign.

**Do:** write the spec, the flag, the docs paragraph, the shelf-life note. **Do
not** implement without a go-ahead. Sequenced after 1–3, because preflight shrinks
the window.

## 6. README and docs

- [ ] **No install step.** "Trying it" opens with a `winthistle` invocation; the
      document never says what language it is written in or how a binary appears.
- [ ] **No requirements/topology section.** Reader infers bitcoind and LND, but not
      where Winthistle runs relative to them, what it needs from each, or which
      signers are known-good for multisig change.
- [ ] **Qualify "no code path in the binary can" replace the funding tx.** True, but
      the network does not enforce it — with full-RBF deployed, the operator's
      *other* wallet can. The discipline lives in the human. State the nSequence
      the batch is built with and why.
- [ ] **No-change batches break the CPFP story.** If coin selection consumes inputs
      exactly, `bump` has nothing to attach to and the funding output cannot be an
      anchor without force-closing. Guarantee a change output above a threshold, or
      document the failure.
- [ ] **The signing session has its own clock.** LND issues funding addresses before
      the PSBT can be built, so shims are open while signers assemble. Reservations
      expire — **read the value out of the vendored LND version rather than trusting
      any doc, including this one.** A slow session burns the shims. Document the
      expected wall-clock budget.
- [ ] **Add "why not just use Sparrow."** Built on item 2: Sparrow signs a
      transaction; Winthistle knows what the transaction means. Best available
      statement of what the tool is for.
- [ ] **Split the status blockquote's second sentence** — the "web interface does not
      exist" clause is buried in a run-on.
- [ ] **`print-macaroon-command` vs `make macaroon`** read as two doors to one room,
      documented separately. Reconcile or cross-reference.

## 7. In-house QR — explicitly out of scope

Recorded so it is not re-litigated. Winthistle writes a `.psbt` and reads a signed
one back; transport is the operator's problem.

A 2-of-3 batch PSBT carries witness UTXOs, ~105-byte witness scripts, three BIP32
derivations per input, and global xpubs — 1–3 KB, several KB base64. Past
single-QR capacity, so multipart is mandatory, so it is BBQr *and* UR2.0 *and*
SeedSigner's scheme, plus camera capture, frame reassembly and image
dependencies. Large spend against the audit constraint, to reimplement what
Sparrow already does under more scrutiny.

Display-only QR is cheap (Unicode half-blocks, `▀`, two modules per cell to cancel
the cell aspect ratio) and covers half the round trip if ever wanted. Camera
capture stays a browser problem. SeedSigner is the genuine forcing case, having no
storage by design, and is where Sparrow-as-bridge earns its keep.

**Docs should state the contract, not the app:** any wallet that round-trips BIP174
with the descriptor works. Naming Sparrow as the only path ages badly, is wrong for
SD-card signers who need no bridge, and is wrong for headless deployments beside
LND where a desktop app is unavailable.

## 8. Freeze the run-directory format; pin down `recover`

Before anything above adds surface. The on-disk state machine is more load-bearing
than any feature — `bump`, `recover` and item 3 all read it. Version it, enumerate
every state a directory can be found in, specify `recover`'s behaviour in each.
